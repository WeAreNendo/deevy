# M1 Humans: vertical slices

Breakdown of the M1 milestone from [PLAN.md](../PLAN.md), 2026-09-03. Vocabulary is [CONTEXT.md](../../CONTEXT.md).
M1 is done when our own team runs its work in deevy on the Docker image, with no Agents yet.

Thirteen slices, in dependency order. Each is one PR on `main` that leaves the image deployable, adds its
operations to the registry, and carries its own tests. Nothing in a slice is needed by an earlier one.

## Decisions taken for M1

- **TanStack Router** for the SPA, next to the existing TanStack Query client. **shadcn** for components, as
  PLAN.md says.
- **Allowlist only, no invitations.** A Workspace admin adds rules (email domain, GitHub organization); a sign-in
  that matches a rule joins as a Member. Per-person invitations are deferred.
- **GitHub sign-in only.** GitLab, Google, and OpenID Connect are a later slice; the allowlist schema keeps a
  `kind` column so a GitLab group rule is additive.
- **Any Human approves any Gate.** Named approvers per Gate wait for M2, where Runs make them matter.
- **Events first.** Every write appends an Event in the same handler, sequentially (no transaction, ADR-0006).
  Notifications, the SSE stream, and the Issue timeline read the Event log; nothing else is a second source.
- **Registry grows two rules**: `admin` (a Member with `role = admin`) and streaming outputs (oRPC event
  iterators) for SSE. Both stay inside `packages/core/src/operations/registry.ts` (ADR-0009).
- **D1 limits shape queries now** (PLAN.md risks): list operations page with a cursor, no per-row queries in a
  loop, multi-row writes are single statements. Not `db.batch`: it exists only on the D1 driver, so anything in
  `packages/core` that reaches for it breaks the Node build (ADR-0006).

## Deferred out of M1

Named Gate approvers; workflow rules that fire on entering a State (M2, they assign Agents); Slack Channels and
routing rules; per-person notification preferences (arrive with Channels); card ordering inside a board column;
private Projects; four-eyes Gates; requester-cannot-approve.

Invitations and the GitLab, Google and OIDC providers were on this list until after v1, when
[sign-in.md](./sign-in.md) built all four; the two M1 decisions above that named them are the record of what
M1 chose, not of what deevy does now.

## Conventions every slice follows

Definition of done for a slice:

1. Schema in `packages/db/src/schema/<area>.ts`, relations merged in `relations.ts`, migration generated with
   `vp run db#generate`, `NOT NULL` patched on text primary keys, `vp run db#check:migrations` green.
2. Operations added in `packages/core/src/operations/index.ts` via `defineOperation`, one namespace per area
   (`projects.*`, `issues.*`). Not-found is `ORPCError("NOT_FOUND")`, duplicates `CONFLICT`, rule violations
   `FORBIDDEN` or `BAD_REQUEST` with a message in CONTEXT.md vocabulary.
3. Every write appends an Event through `appendEvent` (slice 1) before returning.
4. `vp run core#snapshot:openapi` committed.
5. Core tests through `createRouterClient(router, { context })` with the `memberContext` helper (slice 1). SPA
   tests with Testing Library against a mocked `client`.
6. UI in `apps/web/src/routes/<area>` with shadcn components; copy uses CONTEXT.md words.
7. `vp check` clean, `vp run -r test` green, Workers build green (`vp run web#build:workers`).
8. Docker image from the PR boots and serves the new surface.

Sizes below are t-shirt estimates for one developer plus agents: S under a day, M two to three days, L a week.

## Dependency order

```
1 Event log
└─ 2 Membership and SPA shell
   └─ 3 Projects and Teams (seeds the default Workflow)
      └─ 4 Issues
         ├─ 5 Workflow engine (transitions, Gates, approvals)
         │  ├─ 6 Board view
         │  └─ 8 Documents
         ├─ 7 Live updates (SSE)          needs only 1 and 4 for a visible effect
         ├─ 9 Labels
         ├─ 10 Comments and mentions
         └─ 11 Repositories and Links
            12 Inbox                       needs 4, 5, 10 (assignment, Gate, mention)
            13 Dogfood release             needs everything
```

Slices 8 through 11 are independent of one another and can be built in parallel once 5 is in.

## Slice 1: Event log (S)

**Goal.** Every change in the Workspace is an immutable Event with actor and timestamp, readable over the API.
Everything later derives from it (PLAN.md point 3).

**Depends on.** M0.

**Schema.** `event`: `seq` integer primary key autoincrement (the cursor SSE and the inbox use), `workspaceId`,
`actorMemberId` nullable (null for system writes such as bootstrap), `kind` text (`workspace.created`,
`member.joined`, later `issue.created`, dotted `<subject>.<verb>`), `subjectType`, `subjectId`, `projectId`
nullable, `payload` JSON text, `createdAt`. Index on `(workspaceId, seq)`, `(subjectType, subjectId)`,
`(projectId, seq)`.

**Core.** `packages/core/src/events.ts`: `appendEvent(db, event)` returning the row, and a typed `EventKind`
union that grows with each slice. `bootstrapWorkspace` appends `workspace.created` and `member.joined`.
`packages/core/tests/helpers.ts` gains `memberContext(db, { role?, kind? })`: inserts a user, the Workspace if
missing, and a Member, and returns an `AppContext` for `createRouterClient`.

**Operations.** `events.list` (member): input `{ after?: number, subjectType?, subjectId?, projectId?, limit }`,
output events in `seq` order plus `nextCursor`.

**UI.** None. The operation shows in `/api/docs`.

**Acceptance test.** `packages/core/tests/events.test.ts`: bootstrap the admin, call `events.list` as that
Member, expect `workspace.created` then `member.joined` with `actorMemberId` null and the admin's Member as
subject; `after: <first seq>` returns only the second; an anonymous caller gets `UNAUTHORIZED`. OpenAPI snapshot
contains `/events`.

## Slice 2: Membership and the SPA shell (M)

**Goal.** A teammate signs in with GitHub and lands in the Workspace because a rule matched; the admin sees and
manages Members. The SPA gains routing, a layout, and a component library that every later slice uses.

**Depends on.** 1.

**Schema.** `allowlist_rule`: `id`, `workspaceId`, `kind` (`email_domain | github_org`), `value`, `createdBy`,
`createdAt`, unique `(workspaceId, kind, value)`. `member` gains `handle` text unique (for mentions in slice 10),
set on join from the GitHub login when the provider supplies it, else a slug of the name, suffixed on collision.

**Core.** `joinWorkspace(db, user)` next to `bootstrapWorkspace`, called from the same two Better Auth hooks: if
a Workspace exists, the user has no Member, and a rule matches (email domain against the user's email; GitHub
organization against the organizations the sign-in's access token can list, which needs the `read:org` scope
on the OAuth App), insert a Member with `role = member` and append `member.joined`. `buildContext` in `app.ts`
treats a Member with `suspendedAt` set as no Member. Registry gains the `admin` auth rule.

**Operations.** `members.list` (member), `members.updateRole`, `members.suspend`, `members.reinstate` (admin;
an admin cannot suspend or demote the last admin), `allowlist.list`, `allowlist.add`, `allowlist.remove`
(admin). Events: `member.joined`, `member.role_changed`, `member.suspended`, `member.reinstated`,
`allowlist.rule_added`, `allowlist.rule_removed`.

**UI.** TanStack Router with routes `/`, `/settings/members`, `/settings/allowlist`; shadcn initialised; an app
shell with a sidebar (Projects, Inbox, Settings, all but Settings placeholders until their slices) and the
signed-in header from M0. The "signed in, not a Member" page stays and now says an admin can add an allowlist
rule.

**Acceptance test.** Core: with rule `email_domain = example.com`, a session for `bob@example.com` yields a
Member with `role = member`, a `handle`, and a `member.joined` Event; `carol@example.org` yields none; a
suspended Member gets `FORBIDDEN` on `workspace.get`; a non-admin gets `FORBIDDEN` on `allowlist.add`; the last
admin cannot be demoted. SPA: `/settings/members` renders the Member list from a mocked client. Browser: a second
GitHub account with a matching email signs in on the dev server and sees the Workspace.

## Slice 3: Projects and Teams (M)

**Goal.** Work has a home: a Project with a key prefix and a Workflow, optionally owned by a Team.

**Depends on.** 2.

**Schema.** `team`: `id`, `workspaceId`, `name`, `handle` unique, `createdAt`. `team_member`: `(teamId,
memberId)` primary key. `project`: `id`, `workspaceId`, `key` (2 to 6 uppercase letters, unique), `name`,
`description`, `teamId` nullable, `nextIssueNumber` integer default 1, `createdAt`, `archivedAt`.
`workflow_state`: `id`, `projectId`, `name`, `position`, `isGate` boolean, `category` (`backlog | active |
done`, so the board and lists know what "open" means), `createdAt`. Slice 8 adds template columns.

**Core.** `defaultWorkflow()` returns the template from PLAN.md: Intent, Spec, Plan, Build, Review, Done with
Gates on Intent, Spec, Plan, Review. `projects.create` inserts the Project, then its States as one multi-row
statement. Not `db.batch`: that exists only on the D1 driver, so the core cannot use it and stay
runtime-neutral (ADR-0006). A single statement satisfies the same rule.

**Operations.** `projects.list`, `projects.get` (by key), `projects.create`, `projects.update`,
`projects.archive`; `teams.list`, `teams.create`, `teams.update`, `teams.delete`, `teams.addMember`,
`teams.removeMember`. Create and delete are admin; update is admin or a Member of the owning Team. Events:
`project.created`, `project.updated`, `project.archived`, `team.*`.

**UI.** `/` lists Projects with a create dialog (name, key, Team); `/projects/$key` shows the Project header and
an empty Issue list placeholder; `/settings/teams` manages Teams and their Members.

**Acceptance test.** Core: creating Project "deevy" with key `DEV` returns it with six States in order and
`isGate` true on Intent, Spec, Plan, Review; a second `DEV` is `CONFLICT`; `dev` and `TOOLONGKEY` are
`BAD_REQUEST`; a Team with two Members lists both; Events recorded. Browser: create a Project, reload, it is
listed.

## Slice 4: Issues (L)

**Goal.** The unit of work exists: keyed Issues with a description, an Assignee, a parent, in a State, with a
timeline.

**Depends on.** 3.

**Schema.** `issue`: `id`, `projectId`, `number` integer, `title`, `description` markdown text, `stateId`,
`stateEnteredAt`, `assigneeMemberId` nullable, `parentId` nullable, `createdBy`, `createdAt`, `updatedAt`,
`closedAt` (set when the State's category is `done`). Unique `(projectId, number)`; the key `DEV-42` is derived
and never stored twice. Index on `(projectId, stateId)`, `assigneeMemberId`, `parentId`.

**Core.** Number allocation is one statement, safe on D1 and under concurrency:
`UPDATE project SET next_issue_number = next_issue_number + 1 WHERE id = ? RETURNING next_issue_number`. New
Issues enter the first State. Parent must be in the same Project and must not create a cycle.

**Operations.** `issues.create`, `issues.get` (by key, with Assignee, parent, children, State),
`issues.list` (by Project, filters `stateId`, `assigneeMemberId`, `open`, cursor paging), `issues.update`
(title, description, assignee, parent). All member. Events: `issue.created`, `issue.updated`,
`issue.assigned` (payload has old and new Assignee), `issue.reparented`.

**UI.** `/projects/$key` Issue list with a new-Issue form; `/issues/$issueKey` with editable title and markdown
description, State badge (read-only until slice 5), Assignee picker over `members.list`, parent link and
children list, and a timeline rendered from `events.list` for the Issue.

**Acceptance test.** Core: twenty concurrent `issues.create` calls yield numbers 1 through 20 with no gap;
`issues.get("DEV-3")` returns the third; assigning a non-Member id is `BAD_REQUEST`; setting an Issue's parent
to its own descendant is `BAD_REQUEST`; `issues.list({ open: true })` excludes nothing yet (no done Issues) and
pages by cursor. SPA: the Issue page renders key, title, and timeline from a mocked client. Browser: create,
assign, and reparent an Issue and see the timeline grow.

## Slice 5: Workflow engine (L)

**Goal.** Issues move through States; a Gate cannot be left without a Human's approval; a Workflow can be
edited so a team that wants Todo, Doing, Done deletes the middle.

**Depends on.** 4.

**Schema.** `gate_decision`: `id`, `issueId`, `stateId`, `decision` (`approved | rejected`), `note`,
`memberId`, `createdAt`.

**Core.** `packages/core/src/workflow.ts`: `moveIssue(issue, toState)` rejects when the current State is a Gate
(`FORBIDDEN`, "DEV-3 is in the Intent Gate; approve or reject it"); `approveGate` records a decision and moves
the Issue to the next State by position; `rejectGate` records and moves it to the previous State (or keeps it in
place when it is first). Both throw `FORBIDDEN` when `context.member.kind === "agent"` (ADR-0004), so M2 gets
the rule for free. Moving into a `done` State sets `closedAt`; leaving one clears it. Every move sets
`stateEnteredAt`.

**Operations.** `issues.move` (member), `gates.approve`, `gates.reject` (member, Human only),
`workflow.get`, `workflow.update` (admin or owning Team: add, rename, reorder, delete States, toggle `isGate`,
set `category`; deleting a State that holds Issues requires a `moveIssuesTo` State). Events: `issue.moved`
(from, to), `gate.approved`, `gate.rejected`, `workflow.updated`.

**UI.** Issue page: a State select for non-Gate States; in a Gate, Approve and Reject buttons with an optional
note, and the decision history. `/projects/$key/settings/workflow`: ordered State editor.

**Acceptance test.** Core: `DEV-1` starts in Intent; `issues.move` to Spec is `FORBIDDEN`; `gates.approve`
moves it to Spec with a `gate.approved` Event and a `gate_decision` row; `gates.reject` in Spec returns it to
Intent; a Member with `kind = agent` (inserted directly) gets `FORBIDDEN` on approve; Build to Review is a plain
move; moving to Done sets `closedAt` and `issues.list({ open: true })` hides it; deleting Spec, Plan, Build,
Review with `moveIssuesTo` leaves Intent (renamed Todo), Done and relocates the Issues. Browser: walk one Issue
from Intent to Done through the four Gates.

## Slice 6: Board view (M)

**Goal.** The Project's Issues as columns per State, with drag and drop that respects Gates.

**Depends on.** 5.

**Schema.** None.

**Operations.** None new. `issues.list` gains `groupByState` output shape if the flat list proves awkward.

**UI.** `/projects/$key/board`: one column per State in `position` order, Gate columns marked; cards show key,
title, Assignee; drag with dnd-kit; dropping a card out of a Gate column opens the Approve or Reject dialog
instead of moving; filter by Assignee and open/closed. Cards sort by `updatedAt`; explicit ordering is deferred.

**Acceptance test.** SPA: with a mocked client the board renders six columns in order, a drop from Build to
Review calls `issues.move`, a drop out of Intent opens the Gate dialog and calls `gates.approve` on confirm.
Browser: drag a card, reload, it stayed.

## Slice 7: Live updates over SSE (M)

**Goal.** Two browsers see each other's changes without reloading, from an Event-log cursor, with heartbeats,
request-scoped so the same code runs on Workers later (ADR-0006).

**Depends on.** 1 (and 4 to see anything move).

**Schema.** None.

**Core.** Registry accepts an oRPC event-iterator output. `events.subscribe` (member): input `{ after?: seq,
projectId? }`; the handler loops until the request's abort signal fires: read Events after the cursor (one query
per tick, one second apart), yield each, yield a heartbeat every fifteen seconds. No timers survive the request.

**Operations.** `events.subscribe`. The SSE stream is the third surface of ADR-0005 for the UI; webhooks come in
M2.

**UI.** `useLiveEvents()` mounted in the app shell: on each Event, invalidate the queries for its subject (Issue
key, Project list, board, inbox count in slice 12); reconnect from the last seen `seq` after a drop.

**Acceptance test.** Core: subscribe from a test client, create an Issue through another call, the iterator
yields `issue.created` within two seconds; aborting the signal ends the iterator. Browser: two tabs on the board,
move a card in one, the other updates without reload; kill and restart the server, the tab reconnects.

## Slice 8: Documents (M)

**Goal.** Named, versioned markdown on an Issue (intent, spec, plan), each created from the template of the
State that asks for it.

**Depends on.** 5.

**Schema.** `document`: `id`, `issueId`, `name`, `currentVersion` integer, `createdAt`, `updatedAt`, unique
`(issueId, name)`. `document_version`: `id`, `documentId`, `version`, `body`, `authorMemberId`, `createdAt`,
unique `(documentId, version)`. `workflow_state` gains `documentName` nullable and `documentTemplate` nullable.
`defaultWorkflow()` fills Intent, Spec, Plan with the playbook templates from PLAN.md (Problem, Proposed
outcome, Affected users and systems, Constraints, Open questions; requirements, design, flagged concerns; files
that change, order of work, tests that prove it).

**Core.** Entering a State with a `documentName` (on create, move, approve, reject) creates that Document from
the template when the Issue has none. Writes are append-only versions.

**Operations.** `documents.list` (by Issue), `documents.get` (name, optional version), `documents.write`
(new version), all member. `workflow.update` accepts the template fields. Events: `document.created`,
`document.updated` (version number in payload).

**UI.** Issue page Documents section: one tab per Document, markdown editor with preview, version list with
read-only view of older versions. Workflow editor gains the template textarea per State.

**Acceptance test.** Core: creating an Issue creates an `intent` Document at version 1 whose body contains
"## Problem"; `documents.write` makes version 2 and `documents.get` without a version returns it while
`version: 1` returns the template; approving the Intent Gate creates `spec`; a second approval does not create a
second `spec`. Browser: edit the intent, approve, see the spec tab appear.

## Slice 9: Labels (S)

**Goal.** Workspace-level Labels, plain or scoped, at most one per scope on an Issue.

**Depends on.** 4.

**Schema.** `label`: `id`, `workspaceId`, `scope` nullable, `name`, `color`, `createdAt`, unique
`(workspaceId, scope, name)`. `issue_label`: `(issueId, labelId)` primary key.

**Operations.** `labels.list`, `labels.create`, `labels.update`, `labels.delete` (admin for delete);
`issues.setLabels(issueKey, labelIds)` (member) replaces the set and, when two ids share a scope, keeps the last
one given; `issues.list` gains a `labelId` filter. Events: `label.*`, `issue.labels_changed` (added, removed).

**UI.** `/settings/labels`; Label picker on the Issue page showing scoped Labels as `scope: name`; Label filter
on list and board; Labels on cards.

**Acceptance test.** Core: `epic:Checkout` and `epic:Billing` set together leaves only Billing; `backend` and
`frontend` stack; deleting a Label removes it from Issues and appends one Event per affected Issue; duplicate
`(scope, name)` is `CONFLICT`. Browser: filter the board by a Label.

## Slice 10: Comments and mentions (M)

**Goal.** Discussion on an Issue, with `@handle` mentions of Members and Teams that the inbox can act on.

**Depends on.** 4 and 2 (handles, Teams).

**Schema.** `comment`: `id`, `issueId`, `authorMemberId`, `body`, `createdAt`, `editedAt`, `deletedAt`.

**Core.** `mentions(body)` extracts `@handle` tokens, resolves Members and Teams, expands Teams to their
Members; the `comment.created` Event payload carries the resolved Member ids. Mentions in an Issue description
are resolved the same way on `issues.update`.

**Operations.** `comments.list` (by Issue), `comments.create`, `comments.update` (author only),
`comments.delete` (author or admin, soft). Events: `comment.created` (with `mentionedMemberIds`),
`comment.edited`, `comment.deleted`.

**UI.** Comment thread on the Issue page with markdown and an `@` autocomplete over Members and Teams; edited and
deleted markers.

**Acceptance test.** Core: a comment "ping @bob and @core" where `core` is a Team of Bob and Carol produces an
Event whose `mentionedMemberIds` is exactly Bob and Carol; editing someone else's comment is `FORBIDDEN` for a
member and allowed for an admin; a deleted comment stays in `comments.list` with `deletedAt` and no body.
Browser: post a comment with autocomplete.

## Slice 11: Repositories and Links (S)

**Goal.** An Issue points at the code: typed Links to pull requests, commits, branches, and URLs in registered
Repositories.

**Depends on.** 4.

**Schema.** `repository`: `id`, `workspaceId`, `provider` (`github | gitlab | other`), `name` (`owner/repo`),
`url`, `createdAt`, unique `(workspaceId, url)`. `issue_link`: `id`, `issueId`, `kind` (`pull_request | commit
| branch | url`), `url`, `title`, `ref` (PR number, SHA, or branch name), `repositoryId` nullable, `createdBy`,
`createdAt`.

**Core.** `parseLink(url, repositories)` recognises GitHub and GitLab pull request, merge request, commit, and
branch URLs, sets `kind` and `ref`, and matches a Repository by URL prefix; anything else is `url`.

**Operations.** `repositories.list`, `repositories.create`, `repositories.delete` (admin for writes);
`links.list`, `links.add` (a URL and optional title; kind is derived, an explicit kind overrides),
`links.remove`. Events: `repository.*`, `issue.link_added`, `issue.link_removed`.

**UI.** `/settings/repositories`; Links section on the Issue page with paste-a-URL add, grouped by kind, and the
Repository name shown when matched.

**Acceptance test.** Core: with Repository `https://github.com/WeAreNendo/deevy` registered,
`links.add("https://github.com/WeAreNendo/deevy/pull/12")` yields `kind = pull_request`, `ref = "12"`, the
Repository id; a commit URL yields `commit` and the SHA; `https://example.com/design` yields `url` and no
Repository. Browser: paste a PR URL and see it grouped under pull requests.

## Slice 12: Inbox (M)

**Goal.** Each Human has an in-app inbox of Notifications derived from Events: mention, assignment, Gate awaiting
you. Run kinds and Slack arrive in M2.

**Depends on.** 4, 5, 10; 7 for the live badge.

**Schema.** `notification`: `id`, `recipientMemberId`, `kind` (`mention | assignment | gate_awaiting`),
`eventId` (the `seq`), `issueId`, `readAt`, `createdAt`. Index `(recipientMemberId, readAt)`.

**Core.** `deriveNotifications(event)` runs inside `appendEvent` after the insert (same request, sequential):
`issue.assigned` notifies the new Assignee unless they are the actor; `comment.created` and `issue.updated`
notify each mentioned Member except the actor; any Event that leaves the Issue in a Gate State notifies every
active Human except the actor. That last rule is about where the Issue ended up, not how it got there, so
`issue.created`, `issue.moved`, `gate.rejected` and `gate.approved` all count: approving Intent lands the Issue
in the Spec Gate, which needs a Human just as much as the one before it. One row per recipient per Event.

**Operations.** `inbox.list` (`unreadOnly`, cursor), `inbox.unreadCount`, `inbox.markRead(ids)`,
`inbox.markAllRead`. All member, scoped to the caller. Events: none (Notifications derive from Events; marking
read is not a Workspace change).

**UI.** `/inbox` grouped by Issue with kind, actor, time, and a link; unread badge in the sidebar, refreshed by
`useLiveEvents` on any Event.

**Acceptance test.** Core: Alice assigns `DEV-1` to Bob, Bob has one `assignment` Notification and Alice none;
Alice assigns to herself, no Notification; a comment mentioning `@bob` adds a `mention`; `DEV-2` created in the
Intent Gate gives every other Human a `gate_awaiting`, and approving that Gate gives them another for the Spec
Gate it lands in; `markRead` on Bob's ids does not touch Carol's;
`unreadCount` drops accordingly. Browser: open two accounts, assign in one, the badge increments in the other.

## Slice 13: Dogfood release (M)

**Goal.** The milestone's own definition of done: the team runs its work in deevy from the Docker image, and an
upgrade keeps the data.

**Depends on.** 1 through 12.

**Work.** `docs/OPERATIONS.md` (image, volume, env vars, upgrade, backup with `sqlite3 .backup`, restore);
`docker-compose.yml` example; CI publishes the image to GHCR on a `v0.1.x` tag; `/settings/workspace` to rename
the Workspace; the "not a Member" page and `DEVELOPMENT.md` updated for the allowlist; `CLAUDE.md` current
milestone bumped to M2. Then the team creates the deevy Project on the running instance and moves M2 planning
into it as Issues.

**Acceptance test.** On a fresh container from the tagged image with `DEEVY_ADMIN_EMAIL` set: admin signs in,
adds an email-domain rule, a teammate joins; create a Project, walk an Issue from Intent through the Gates to
Done with a Document, Labels, a comment with a mention, and a PR Link; both people see the board update live and
the inbox fill. Stop the container, start the next tag on the same volume, everything is still there and
`/healthz` answers. One week of the team's real work in it without falling back to another tool.
