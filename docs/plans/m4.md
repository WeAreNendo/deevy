# M4 Reference runtime: vertical slices

Breakdown of the M4 milestone from [PLAN.md](../PLAN.md), 2026-09-05. Vocabulary is
[CONTEXT.md](../../CONTEXT.md); M1's slices are in [m1.md](./m1.md), M2's in [m2.md](./m2.md) and M3's in
[m3.md](./m3.md). M4 is done when the loop that [agent-loop.md](../agent-loop.md) describes in prose is
software in this repository: a service holding one Agent's key that picks up assigned Issues, works them,
stops at Gates, resumes after a Human rules, and finishes with evidence — running against either deployment
shape, tested on every commit, and documented for an operator who has neither.

Ten slices, in dependency order. Each is one PR on `main` that leaves both deevy deployments unchanged and
carries its own tests. Nothing in a slice is needed by an earlier one.

M4 is the first milestone whose subject is not deevy. Nine of these ten slices add no operation, no table and
no route: they build the thing on the other side of the surfaces M2 and M3 shipped, and the interesting
failures are all failures of those surfaces to be usable by a stranger. That makes the slices easy to get
wrong in one particular way — reaching into `packages/core` for a type or a helper when the surface does not
offer one — so the rule below about what the runtime may depend on is the one to break last.

## Decisions taken for M4

- **The runtime is a peer, not a component.** It lives at `apps/claude-agent`, inside the pnpm workspace so
  `vp check` and `vp run -r test` cover it and CI drives it against a real deevy on every commit. But it may
  not import `packages/core` and may not take a `workspace:*` runtime dependency: it speaks MCP and HTTP like
  any third party, which is the only way it tests ADR-0005's claim rather than restating it. Its
  devDependencies are the exception and may reach into the workspace, because standing up a real deevy to
  test against is what they are for; a test asserts that split. The cost is a documented copy step for
  somebody lifting it into their own repository, since `catalog:` version refs resolve only in here.
- **The Claude Agent SDK, not the `claude` CLI.** `query({ prompt, options })` from
  `@anthropic-ai/claude-agent-sdk` returns an async generator of `SDKMessage`, so the seam every test in this
  milestone hangs off is a function rather than a subprocess: a fake session is an async generator yielding
  scripted messages that call back into a real deevy. Shelling out to `claude -p` would make the same seam a
  child process, a PATH, and an argv string nobody can typecheck. `agent-loop.md`'s worked example stays true
  — it describes the CLI configuration a person can copy — and this is the same thing with a program in the
  driver's seat.
- **A long-running service, not a GitHub Action.** PLAN.md's M4 sentence says "Claude Code headless in a
  GitHub Action and as a local loop"; M4 ships the loop and a container, and no Action. An agent that thinks
  for twenty minutes bills twenty minutes of runner time, a Run stopped at a Gate may wait days, and a fresh
  runner per Run pays for a clone it then throws away. The same code runs on a laptop and in a small
  container, woken by a webhook or by polling, and neither is metered by the minute. This is a deviation from
  the plan, so slice 10 records it in an ADR the way M3 recorded the `Cron` port.
- **deevy is the memory; a session is not.** The SDK will happily `resume` a session id, and the runtime does
  not use it. A Run picked back up after a Gate ruling gets a fresh session whose prompt is rebuilt from
  deevy — the Issue, its Documents, its Activity feed, and the ruling with its note. That costs re-reading on
  every resume and buys the property the whole design turns on: the service can restart, move host, or be
  replaced by a second copy mid-Gate and nothing is lost, because nothing was ever only in it. It is the same
  reason the work queue is `runs.list` and not a file on disk.
- **Nothing is claimed locally.** Discovery is `runs.list` with no arguments, which M2 made mean "my own
  Runs" precisely so an Agent that cannot learn its own Member id can still find its work: `pending` is the
  queue and `awaiting_input` is the Runs owed a ruling. The claim is deevy's one-open-Run-per-Issue rule, so
  two services sharing a key is a `CONFLICT` rather than two attempts at one outcome, and a container that
  starts with an empty disk is not a container that starts from scratch.
- **Denial is the default, and the options object is the security boundary.** Every session is built with
  `strictMcpConfig: true` and `settingSources: []`, so nothing in the working directory — a cloned
  repository's `.mcp.json`, its `.claude/settings.json` — can add a server or grant a permission. Tools are
  granted by an explicit `allowedTools`, with `permissionPrompts: "none"` so an unlisted tool is refused
  rather than left waiting for a person who is not there. `permissionMode: "bypassPermissions"` is never
  used; the SDK's own documentation says to prefer an allowlist, and a headless agent is exactly the case it
  is talking about.
- **Issue text is untrusted input, and it reaches a session holding Bash.** Descriptions, Documents, comments
  and other Agents' Activities are written by anyone with Project access. From slice 5 the session also has
  file and shell tools in a checked-out repository, and no prompt makes that safe. What bounds it is
  structural: the container is the sandbox, the allowlist is the tool surface, the git credential is scoped
  to one repository and opens pull requests rather than pushing to a default branch, and a Human at a Gate
  decides whether anything ships. That is an ADR in slice 10, not a paragraph in a README.
- **The repository an Agent works in is the runtime's configuration, not deevy's data.** deevy's Repository
  rows exist so an Issue can point at code; they carry no credential and are not a checkout instruction. One
  service is configured with one repository and one git credential, which is also how a coding agent is
  actually deployed. An Agent granted several Projects across several repositories is several services, and
  that is a feature of the boundary rather than a limitation of it.
- **No test spends money.** Every acceptance test below runs with no Anthropic credential, against a real
  deevy, with a scripted session. A live test that calls the model exists, is guarded by `DEEVY_AGENT_LIVE=1`,
  and CI does not set it. A milestone whose test suite needs a paid key is a milestone nobody runs twice.
- **deevy changes once, and it is debt rather than scope.** Slice 1 is the only slice that touches
  `packages/core`, and it closes a hole M2 left: an Agent told to find work through `inbox_list` with
  `unreadOnly` can never mark a row read, so the same Notification comes back forever. Everything else in M4
  is built on the surfaces as they stand, and a slice that wants to widen one has found something to argue
  about rather than something to add.
- **M3's acceptance has been executed.** The runbook in [m3-acceptance.md](../m3-acceptance.md) was walked on
  a real Cloudflare account with a real GitHub OAuth App, both since torn down. PLAN.md and CLAUDE.md still
  say it has not been run; slice 10 corrects them. M4 carries no M3 debt.

## Deferred out of M4

A GitHub Action, for the billing reason above — if somebody wants one, the service already runs anywhere and a
self-hosted runner is the cheap way to it. Agent-to-agent delegation through sub-issues, and cost and time
accounting per Run, which are both on PLAN.md's after-v1 list and both want the runtime to exist first. More
than one Agent per service. A runtime for anything but Claude: the seam is a function returning an async
generator of SDK messages, which is a shape another runtime could satisfy, and generalising it before there is
a second one would be guessing. The Slack app, email Channels, private Projects, four-eyes Gates, the Postgres
adapter and a CLI, all unchanged from PLAN.md's after-v1 list.

## Conventions every slice follows

M1's eight-step definition of done ([m1.md](./m1.md)), M2's five additions ([m2.md](./m2.md)) and M3's four
([m3.md](./m3.md)) hold unchanged where a slice touches deevy. Only slice 1 does. M4 adds four that apply to
`apps/claude-agent`:

19. No `packages/core` import and no `workspace:*` entry in `dependencies`. devDependencies may reference the
    workspace, because a test needs a real deevy to talk to. A test reads the package's own `package.json`
    and asserts both halves, so the boundary cannot erode by accident.
20. Every test runs with no `ANTHROPIC_API_KEY`. Anything that calls the model is guarded by
    `DEEVY_AGENT_LIVE=1`, skipped when it is unset, and absent from CI.
21. A session's options are asserted whole, never sampled. `allowedTools`, `disallowedTools`,
    `strictMcpConfig`, `settingSources`, `permissionPrompts` and `cwd` are one object and one snapshot: a
    test that checks three of them passes while a fourth is silently missing, and the fourth is the one that
    matters.
22. The runtime's configuration joins the same table in `docs/OPERATIONS.md` that M3 built, with the same
    columns: the variable, the default, and what breaks when it is absent. A knob that exists only on the
    runtime says so.

Sizes are t-shirt estimates for one developer plus agents: S under a day, M two to three days, L a week.

## Dependency order

```
M3
├─ 1 An Agent can clear its own inbox        touches deevy; no runtime dependency; parallel from day one
└─ 2 The runtime works a Run
   └─ 3 The Agent SDK drives it
      ├─ 4 The loop, and the image
      │  └─ 8 A webhook wakes it
      ├─ 5 A working directory, and the tools that touch it
      │  └─ 6 A branch, a pull request, a Link
      └─ 7 Resuming after a ruling
         9 Docs for the runtime and both targets     needs 4 through 8
         10 M4 release: v1                           needs everything
```

Slices 5 and 7 are independent of one another and can be built in parallel once 3 is in. Slice 1 depends on
nothing and is first because carried debt that waits for the release slice is how it becomes M5's.

## Slice 1: An Agent can clear its own inbox (S)

**Goal.** An Agent that finds its work through the inbox can stop finding the same work.

**Depends on.** M3.

**Schema.** None.

**Core.** `inbox.markRead` gains `agents: true`. It gains nothing else: the handler has scoped its update to
`recipientMemberId = context.member.id` in the same statement since M1, so there is no new rule to write and
no way for one Member to mark another's inbox read by guessing ids — the reason to make it an Agent's is that
the safety was already there.

It does **not** gain `mcp: true`, and that is deliberate. PLAN.md promises a twenty-tool set and M3 slice 1
spent a slice making the promise true; a twenty-first tool for the loop's own bookkeeping would undo that for
no benefit, because the caller is the supervisor rather than the model. The supervisor holds the same key and
reaches `POST /api/inbox/read` with it, which is the same authorisation through the other surface (ADR-0011),
and `openapi.json` moves while `mcp-tools.json` does not.

**Why now.** [agent-loop.md](../agent-loop.md) already tells an Agent to call `inbox_list` with
`unreadOnly: true` and already notes that `runs_list` is "the one that still works when the inbox has been
read". Nothing could read it. An Agent's unread count grows without bound, every Gate reminder re-unreads a
row nobody can clear, and the first discovery strategy in the worked example is write-only. M4's runtime hits
this on its first pass, and this is the last slice in which fixing it is a one-line change rather than a
workaround in somebody else's package.

**Acceptance test.** Core: an Agent marks two of its own Notifications read and `inbox.list` with
`unreadOnly` stops returning them; an Agent passing ids belonging to another Member reads zero rows and
changes nothing; a suspended Agent is refused like any other operation; `mcp-tools.json` still lists exactly
twenty tools and `inbox_mark_read` is not among them. The snapshot diff in CI is what keeps that last
sentence honest.

### Found by building the slice

Two of the sentences above were wrong, both in the direction of thinking deevy knew less than it does.

`openapi.json` does not move. The slice expected it to gain the operation; the operation has been in the
spec since M1, because `agents` is a middleware rule about who is asking and not a fact about the HTTP
surface. Only `mcp-tools.json` can move on an `agents` change, and it did not, which is the whole claim. The
snapshot that actually caught the widening was neither: `agents.test.ts` asserts the complete list of
operations carrying `agents: true`, so ADR-0011's default-deny is a list somebody has to edit on purpose.
That test is the guard M4 relies on, and it works.

The stale comment was in `mcp-tools.test.ts`, next to `runs_list`: "its inbox is always empty because
Notifications are derived for Humans". That was true when M2 slice 9 wrote it and stopped being true in M3,
which added `run_answered` and split the kinds into two audiences — and an assignment has always gone to
whoever was assigned, Agent included. So the inbox path this slice unblocks was already carrying both things
the runtime needs, and only the clearing was missing. The comment is corrected in the same PR.

One thing worth carrying into slice 2: `me.get` is on the Agent list. The `runs_list` comment says an Agent
"cannot learn its own Member id", which was also true once. It can, so the supervisor can name itself when it
needs to rather than relying on the argument-free form of `runs.list` meaning "mine".

## Slice 2: The runtime works a Run (L)

**Goal.** A program in this repository finds an Issue assigned to an Agent, opens or adopts its Run, drives
it to a finish, and leaves the Event log saying so — with a scripted session standing in for the model.

**Depends on.** M3, and slice 1 for the inbox path.

**Schema.** None. Nothing in deevy changes in this slice or in any slice after it.

**Work.**

- `apps/claude-agent`, a workspace package named `claude-agent`, with the dependency rule from convention 19
  in force from its first commit. `readConfig(env)` in the shape `apps/server/src/env.ts` established:
  `DEEVY_URL`, `DEEVY_AGENT_KEY`, the poll interval, the per-Run timeout, and nothing read at module scope.
- **Discovery.** `runs.list` with no arguments and `status: "pending"` is the queue; the same call with
  `awaiting_input` is the set of Runs owed a ruling, which slice 7 acts on and this slice only counts.
  `inbox.list` with `unreadOnly: true` is the second way in, filtered to `assignment`, marked read through
  slice 1 once its Issue has been taken up. Both are one HTTP call with the Agent's key as a bearer token,
  through a thin typed client written by hand — not generated, not imported: forty lines of `fetch` that
  prove the OpenAPI surface is usable without a code generator.
- **Claiming.** A `pending` Run is already this Agent's and needs no claim. An Issue found through the inbox
  with no open Run gets `runs.start`, and a `CONFLICT` from it is not an error: it means another copy of the
  service, or an earlier pass, is on it, and the right response is to move to the next Issue.
- **The session seam.** `type Session = (input: SessionInput) => AsyncIterable<SDKMessage>`, which is the
  shape `query()` already has. `workRun({ deevy, session, ... })` takes one, and this slice passes a fake
  that yields scripted messages and calls back into deevy over HTTP exactly as the model would. Slice 3
  passes the real one. Every acceptance test in M4 that says "with a scripted session" means this.
- **The envelope.** Whatever the session does, the Run does not rot. A throw, a timeout, or a session that
  ends without calling `runs_finish` all produce `runs.postActivity` with `kind: "error"` naming what
  stopped it, then `runs.finish` with `failed`. A Run that finished itself is left alone. This is the part
  the worked example asks an agent to remember and a program should not have to.

**What must stay true in deevy.** Nothing changes. If this slice finds it needs an operation that does not
exist, that is a finding to write down in the slice, not an operation to add: every one of them is a claim
about the surfaces being complete, and the answer is more likely to be that the runtime is reaching for
something the design deliberately withheld.

**Acceptance test.** Runtime, against a real deevy started in-process for the test (the Node entry over a
loopback port, with a seeded Workspace, Project, Agent and key): an Issue assigned to the Agent is
discovered, its `pending` Run adopted, and a scripted session that posts two Activities and writes the `plan`
Document and calls `runs_finish` leaves the Run `completed`, the Document at version 1, and the Event log
carrying `run.started`, two `run.activity`, and `run.completed` with the Agent as actor. A second pass finds
nothing to do. A scripted session that throws leaves the Run `failed` with an `error` Activity naming the
throw, and never `active`. A session that returns without finishing leaves the same. Two `workRun` calls
racing one Issue produce one Run and one `CONFLICT`. An Issue in a Project the Agent was not granted is
invisible rather than refused, which is M2's rule seen from the other side. Package: `dependencies` contains
no `workspace:*` and no `@deevy/*`.

### Found by building the slice

**The seam is the runtime's own event union, not `AsyncIterable<SDKMessage>`.** The decision above named the
SDK's shape; the SDK's shape turned out to be a union of thirty-eight message kinds, and `subtype ===
"error_during_execution"` is not a fact about a Run. So `Session` yields four events the runtime owns —
`ready`, `tool`, `text`, `done` — slice 3 maps the SDK's messages onto them in one tested function, and every
test in this package scripts a session in four lines instead of constructing SDK objects. The seam is still a
function returning an async iterable, which was the point.

**Tests reach deevy through the app's own handler, not a loopback port.** `createApp` returns a Hono app, and
a `fetch` that calls `app.request` goes through the same routing, the same middleware and the same API-key
authentication a deployed instance uses, with nothing to bind and nothing to wait for. The client takes its
`fetch` as an option, which is a seam worth having anyway. A real socket is exercised by slice 3's live test
and by slice 4's container test, which is where it proves something the handler cannot.

**The claim is honest about its window.** Only a `pending` Run is taken up, because deevy moves a Run to
`active` on its first Activity and an `active` one is being driven by whoever posted it. That does not close
the gap between listing a Run and posting into it, and no operation deevy offers would — there is no
conditional update on the surface. One service per Agent key is the supported shape, `runs.start`'s
`CONFLICT` is what makes two of them safe against duplicate _Runs_, and this is written down rather than
claimed away.

## Slice 3: The Agent SDK drives it (M)

**Goal.** The scripted session is replaced by Claude, configured so that what it may do is a decision this
repository makes and a test asserts.

**Depends on.** 2.

**Work.**

- `@anthropic-ai/claude-agent-sdk` as the one runtime dependency that matters, pinned exactly in the catalog
  beside the other pre-release lines, for the reason PLAN.md's risks give for all of them.
- `buildSession(config)` returning the real `Session`, whose options are one object and the whole security
  boundary:
  - `mcpServers: { deevy: { type: "http", url: config.mcpUrl, headers: { Authorization: "Bearer …" } } }` —
    the same endpoint and the same credential `agent-loop.md` puts in a `.mcp.json`, built in code so the key
    never lands in a file.
  - `allowedTools` naming the deevy tools this runtime uses, `mcp__deevy__`-prefixed. A wildcard is tempting
    and wrong: the point of listing them is that adding a twenty-first tool to deevy does not silently widen
    what this program may do.
  - `strictMcpConfig: true` and `settingSources: []`, so the session's configuration is what this function
    built and not what happened to be on disk. From slice 5 there is an untrusted repository on that disk and
    this is what stops it configuring anything.
  - `permissionPrompts: "none"`, so an unlisted tool is denied rather than parked on a prompt nobody will
    answer. `permissionMode` stays `"default"`; `"bypassPermissions"` appears nowhere in this repository.
  - `cwd` at a scratch directory created for the Run, empty until slice 5.
  - `systemPrompt` as the `claude_code` preset with an appended instruction file — the `CLAUDE.md` snippet
    from [agent-loop.md](../agent-loop.md), moved out of prose and into `apps/claude-agent/src/instructions.md`
    where it ships. The doc keeps a copy for a human to read and gains a line saying which one is the
    original.
  - `model` and `effort` as configuration, defaulting to `claude-opus-5` and `high`; `maxTurns` and an
    `abortController` wired to the per-Run timeout, so a session that will not stop is stopped and lands in
    slice 2's envelope.
- **Reading the stream.** The `system` init message carries `mcp_servers` with a status per server: a `deevy`
  that is `failed` or `needs-auth` aborts the Run before a token is spent, because a session that cannot
  reach deevy will improvise, and improvising is exactly what nobody wants from it. `assistant` messages'
  `tool_use` blocks are logged locally. The `result` message's `subtype` decides the outcome.
- **What the runtime does not do.** It does not post Activities on Claude's behalf. The instructions tell the
  model to narrate through `runs_post_activity`, and a supervisor that also narrates produces two accounts of
  one Run. The supervisor writes exactly two things the model cannot: the envelope, and slice 6's evidence.

**Acceptance test.** Runtime: `buildSession`'s options for a representative config match a committed
snapshot, whole — the tools list, both isolation flags, the permission fields, the model, the header's
shape with the key redacted. Adding a tool to `mcp-tools.json` does not change the snapshot, which is the
statement that deevy widening is not this program widening. A stubbed generator emitting an init message
whose `deevy` server is `failed` aborts before any tool call and finishes the Run `failed` naming the
connection. A `result` of `error_during_execution` lands in the envelope. A session that runs past the
timeout is aborted and the Run says so. Live, behind `DEEVY_AGENT_LIVE=1` and not in CI: a real session
against a real deevy works the plan Document and the Run reaches the Plan Gate.

### Found by building the slice

**`permissionPrompts: "none"` is exactly what it needed to be**, and the SDK's own type declaration says so
in as many words: the permission mode, rules and hooks still decide, anything that would otherwise prompt is
denied immediately with a message telling Claude there is no approval surface, and `canUseTool` is never
called. That is the right default for a headless run and it made `canUseTool` unnecessary in this slice.
`permissionMode` has six values in this version rather than the four the documentation page lists; the one
this repository uses is `"default"`, and a test says the other five do not appear.

**The abort bridge came out as its own function.** `query` wants an `AbortController` it owns and the
supervisor has an `AbortSignal` built from the Run's timeout and the process's stop. Joining them inside
`buildSession` would have made the only testable part of the real session reachable only by spending money,
so `linkAbort` is exported and tested on its own — including that it lets go of the signal, because a
long-lived signal collecting one listener per Run is a leak the loop in slice 4 would have found first.

**The child process inherits the environment, `DEEVY_AGENT_KEY` included.** Not a new exposure — the key is
already in this process and the session already holds it in a header — but from slice 5 that environment is
visible to a shell running code from a repository, and this is where that becomes a decision rather than an
accident. Slice 5 owns it.

**The options object is asserted inline rather than against a committed snapshot file.** The convention asked
for the whole object, not for a particular mechanism, and an inline literal shows the security boundary in
the pull request diff where a reviewer is already looking. A file snapshot would have shown `1 file changed`.

## Slice 4: The loop, and the image (M)

**Goal.** Something that stays up: on a laptop with `vp dev`, and in a container beside deevy's own.

**Depends on.** 3.

**Work.**

- `startLoop({ intervalMs, … })` around slice 2's `workRun`: one Run at a time, a poll interval that backs
  off while there is nothing to do and resets the moment there is, and no overlapping passes. It is
  deliberately the same shape as `startRunner` in `apps/server` — a timer, a drain, an overlap guard and a
  stop that waits — because M2 already argued that shape out and a second one would be a second set of bugs.
- `--once`, which runs a single pass and exits, for a cron, a person debugging, and slice 10's acceptance
  walk.
- **SIGTERM finishes the sentence.** A stop with a Run in flight aborts the session, posts the `error`
  Activity naming the shutdown, and fails the Run before exiting. A container restart must not leave a Run
  `active` and silent for thirty minutes until deevy's sweep calls it `stale`, because `stale` tells a Human
  nothing about why.
- `apps/claude-agent/Dockerfile` built the way `apps/server`'s is, and a `docker-compose` addition beside the
  existing file so the pair comes up together: deevy on 3000 and the runtime pointed at it. The image is not
  published by `release.yml` in this slice; slice 10 decides whether v1 ships one or ships the recipe.

**Acceptance test.** Runtime: the loop with a stub clock makes one pass per interval and never two at once;
with nothing to do it backs off to the configured ceiling and returns to the floor on the first Run it finds;
`stop()` waits for the pass in flight; SIGTERM mid-session leaves the Run `failed` with an Activity naming
the shutdown, and the process exits without a leaked timer. Container, in CI beside the existing Docker
smoke: `docker compose up` with a seeded deevy, an Issue assigned to the Agent, and a scripted session baked
into the image works the Run to `completed` — which is the first test in M4 that proves the two images talk
to each other over a network rather than over a loopback port.

### Found by building the slice

**A sequential loop needs no overlap guard.** `startRunner` in `apps/server` has one because a timer can fire
into a pass that has not finished. This loop is `while (!stopped) { pass; wait; }`, so the property holds by
construction rather than by care, and the test asserts it by counting sessions rather than by inspecting a
flag.

**The Agent SDK stays out of the bundle.** `vp pack` will happily inline its JavaScript, and doing so buys
nothing: the bundled code still resolves a platform-specific CLI binary at runtime, so the dependency has to
be installed either way and bundling only hides it. `deps: { neverBundle: [...] }` takes it out, the bundle
drops from 1.6 MB to 16 kB, and the runtime image installs exactly the version the catalog pins.

**The container smoke proves less than the slice asked for, on purpose.** The plan wanted a Run worked end to
end inside a container. Doing that without a model means baking a scripted session into the image, which puts
test scaffolding in the artefact an operator runs. So the smoke proves what a container can prove without
that: the image builds, starts, reads its configuration, reaches a real deevy over a real socket, and is
refused with deevy's own word when the key is not a Member — both assertions run against real containers
before they were written down. Everything about what the runtime does with a Run is a test in
`apps/claude-agent` against a real deevy and a scripted session, and the end-to-end-with-a-model claim is the
live test and slice 10's walk.

**`BETTER_AUTH_URL` has to stay loopback in the smoke.** Better Auth refuses a plain-http MCP resource that is
not localhost, so a deevy container told its origin is `http://deevy:3000` will not start at all. It is the
OAuth issuer and the runtime authenticates with an API key, so the two are independent — but it cost a
container that exited before serving anything, and the CI job now says why.

**Failing to start is a message, not a stack trace.** A missing `DEEVY_URL` and a key deevy will not accept
are the two things every operator will hit first, and both now print one line naming the cause and exit 1.
That is also what makes them assertable in CI.

## Slice 5: A working directory, and the tools that touch it (L)

**Goal.** The session gets a repository, a shell, and the tools to use them, inside a boundary this slice
draws on purpose.

**Depends on.** 3.

**Work.**

- **A working directory per Run**, created before the session and removed after it, whatever the outcome. The
  repository is cloned into it from `DEEVY_AGENT_REPO` with the credential in `DEEVY_AGENT_GIT_TOKEN`, at the
  configured base branch. A clone per Run is the honest default — it is the only way two Runs cannot see each
  other's half-finished work — and a documented cache directory is the knob for people whose repository makes
  that painful.
- **The tool surface widens**, and every addition is written down with what it is for: `Read`, `Write`,
  `Edit`, `Glob`, `Grep` for the checkout; `Bash` for the build and the tests; `WebSearch` and `WebFetch`
  for documentation the Issue points at. `disallowedTools` names what must never run even though it would
  otherwise be reachable, and the snapshot from slice 3 grows to cover both lists.
- **The isolation earns its keep now.** `settingSources: []` and `strictMcpConfig: true` were free in slice 3
  and are load-bearing here: the directory now holds a repository somebody else wrote, and a `.mcp.json` in
  it must add no server, a `.claude/settings.json` in it must grant no permission. That is a test, not an
  assumption.
- **The container is the sandbox** and the documentation says so plainly. The credential is scoped to one
  repository. The runtime never runs as root in its image. What a shell inside that container can reach is
  the boundary, and a laptop running the loop directly does not have one — which is a sentence for
  `OPERATIONS.md` rather than a feature to build.

**Acceptance test.** Runtime, with a scripted session and a bare git repository on disk as the remote — no
GitHub and no network: the working directory is created, holds the clone at the base branch, and is gone
after the Run whether it completed or failed. Two Runs in the same pass get different directories and neither
sees the other's files. A repository containing a `.mcp.json` naming a second server and a
`.claude/settings.json` granting `Bash(rm:*)` produces a session whose options snapshot is byte-identical to
one cloned from a repository containing neither — the injection test, and the reason both flags exist. A
session that calls a tool outside the allowlist is denied, the denial is recorded in the Run's feed, and the
Run continues rather than dying. Failure to clone finishes the Run `failed` with an Activity naming the
repository, before the session starts.

### Found by building the slice

**The hole slice 3 flagged was bigger than an inherited variable.** `Bash` plus `DEEVY_AGENT_KEY` is the tool
allowlist with a hole in it: a session could reach any operation the Agent may call over `curl`, including
the ones deliberately left out of `deevyTools`. So the session's process gets an explicit `env` — this
process's, minus the runtime's own secrets — and the git credential goes with it, because the supervisor
clones and pushes and the session has no use for it. That is the first thing in M4 that would have been a
real vulnerability rather than an inconvenience.

**The credential never touches the working directory.** A token in the remote URL is written into
`.git/config`, which the shell can read. `git -c http.extraHeader=...` is not persisted, so the clone the
session gets carries no credential at all, and a test reads `.git/config` back to say so.

**The tool surface follows the configuration, not a flag.** No repository, no shell: a session with nothing
to run has no use for one, and making the widening a consequence of `DEEVY_AGENT_REPO` means nobody gets a
shell-capable agent by forgetting to set something. It also keeps every test written before this slice
meaningful, because they all run in the narrow mode.

**`disallowedTools` earns four entries and no more.** The supervisor owns git and the credential to use it,
so `git push`, `git remote`, `git config` and `gh` are denied: that makes the ownership enforced rather than
hoped for. Nothing else is listed. A denylist beside an allowlist invites the belief that the allowlist has
holes this patches, and it does not.

**The injection test can prove half of what it wants, and says which half.** The repository really does
contain a hostile `.mcp.json` and a `.claude/settings.json` — the test asserts they are in the clone — and
the options this runtime builds are byte-identical to the ones for a clean repository. That the SDK honours
`settingSources: []` and `strictMcpConfig: true` is not something a test can show without running a session,
so it is the live test's to prove and this one asserts that the runtime asks for them.

**A refused tool is the one thing the model cannot report accurately about itself.** With no approval surface
the session only sees an error, and will often narrate it as something else. `SDKPermissionDeniedMessage`
becomes a `denied` event, the supervisor writes it into the feed, and the Run carries on — capped at five per
Run, so a session in a loop does not fill the feed. It is the second thing the supervisor narrates, and the
exception proves the rule.

**Posting an Activity moves the Run to `active`.** Obvious in hindsight and it cost two tests: a denial
recorded before the model has posted anything starts the Run, so a session then looking for a `pending` Run
finds none. That is the correct behaviour — the session did start — and the tests hold the Run they mean
rather than re-querying for it.

## Slice 6: A branch, a pull request, and a Link (M)

**Goal.** What the Run produced is attached to the Run that produced it, which is the last sentence of the
scenario every milestone since M2 has been walking.

**Depends on.** 5.

**Work.**

- A branch per Run, named from the Issue key and the Run's id so two attempts at `DEV-42` cannot collide, cut
  from the base branch and pushed. Nothing pushes to the base branch, ever: the credential should not be able
  to, and the runtime does not try.
- A pull request opened through a small `Forge` interface with a GitHub implementation, so the pull-request
  step has a stub in tests and one real implementation in production. Its URL goes to `links.add` with the
  Run's id, which is what M2 slice 2's `issue_link.runId` was for and what M3 slice 1 made an Agent able to
  manage.
- The Run's own summary names the branch and the pull request, because `runs.finish` is what a Human reads
  first and a summary that says "done" is worth nothing.
- A Run that changed no file attaches nothing and says so. An empty pull request is a worse record than none.

**Acceptance test.** Runtime, against the bare repository from slice 5 and a stub `Forge`: a scripted session
that edits a file produces a branch named from the Issue key and the Run id, one commit, a push, one call to
the stub, and one `issue_link` carrying the Run's id and the returned URL. A second Run on the same Issue
gets a different branch and does not touch the first's. A session that changed nothing pushes nothing and
adds no Link. A push that fails finishes the Run `failed` with the git error in an Activity, and the branch is
not half-attached. Deevy: the Link is visible on the Issue and attributed to the Run, and the Agent can remove
its own and not another's — M3 slice 1's rule, seen from the runtime.

### Found by building the slice

**The evidence cannot be an Activity, and the slice was wrong to say it could.** The model finishes its own
Run, a finished Run takes no more Activities, and the branch does not exist until the session is over — so by
the time there is anything to report the feed is closed. The Link still works and is the structured record,
carrying `runId`; what a Human reads on the Issue is a comment. Two of this slice's tests found that, and
they found it because they asserted against a real deevy rather than a mock that would have accepted
anything.

**The Run's summary cannot name the pull request either, for the same reason.** The slice said it would. The
summary is the model's, written at `runs_finish`, before the push. The comment names both the branch and the
pull request, and the Link ties them to the attempt.

**A repository with no forge still ships a branch.** No credential, or a repository that is not on GitHub,
means `forgeFor` returns null and the Run pushes its branch and says so. That is a smaller record rather than
a broken one, and it is also what makes every test in this slice runnable against a bare repository on disk
with no network at all.

**Delivery failing does not fail the Run.** The work happened; only the record of it did not. The Run's own
outcome stands, and a comment says what went wrong — a Run marked failed over a push that could not reach the
remote would be the same lie as failing one over work that succeeded.

## Slice 7: Resuming after a ruling (M)

**Goal.** The milestone's headline sentence: the Human approves in deevy and the loop carries on.

**Depends on.** 3.

**Work.**

- A Run in `awaiting_input` is not new work and not stale work. Each pass calls `runs.requestApproval` for
  it, which M2 built to be the question and the answer at once: `pending` means wait, and `approved` or
  `rejected` carries the Gate, the deciding Human and their note, and lands the ruling in the Run's own feed
  as a `prompt` Activity.
- A ruling starts a **fresh session**, per the decision above, with a prompt that names what happened and
  what to do about it: approved means carry on into the State the Issue is now in, rejected means read the
  note and revise the Document it is about. The Issue, its Documents and the Activity feed are read back over
  MCP by the session itself, which is why nothing needs to be carried across.
- Rejection is not a retry. The runtime never calls `runs.requestApproval` again for a Gate that answered
  `rejected` until the Document has been written again — otherwise a rejected plan asks the same question in
  a loop, and the Human who wrote the note watches their inbox fill with it.
- A Run stuck at `pending` for longer than a configured patience is left alone and logged, not failed.
  `agent-loop.md` is already right about this and the runtime must not be more impatient than the design: a
  Run waiting on a Human does not go stale, and deevy re-asks the approvers on its own.

**Acceptance test.** Runtime, against a real deevy with a scripted session: a Run driven to
`runs_request_approval` is left `awaiting_input` and the next pass does not restart it. A Human approving
through the HTTP API as a Human moves the Issue on, and the following pass resumes the Run, finishes it
`completed`, and the Event log reads `run.awaiting_input`, `gate.approved` with the Human as actor,
`run.activity` for the ruling, `run.completed` — the Agent as actor throughout and the Human exactly one hop
away. A rejection with a note reaches the next session's prompt verbatim and produces a second version of the
Document rather than a second identical question; the Gate is asked again only after that write. A ruling
made while the service is stopped is picked up on the first pass after it starts. A Run left `awaiting_input`
past the patience window is still `awaiting_input`, and the pass says why.

### Found by building the slice

**The runtime never polls a Gate, and the slice was wrong to think it would.** The plan had each pass calling
`runs.requestApproval` for every `awaiting_input` Run, with a rule against re-asking a rejected one and a
patience window for a Run nobody rules on. None of that is needed. deevy already moves a Run from
`awaiting_input` to `active` the moment a Human rules and appends `run.answered`, which lands in the Agent's
inbox — which is exactly what M3 added `run_answered` for. So the resume queue is the inbox, the runtime is
told once per ruling, and "rejection is not a retry" is a property of the design rather than a rule anyone
has to keep. The patience window is gone with it: a Run nobody has ruled on is simply never handed back.

That also justifies slice 1 twice over. Without `inbox.markRead` an Agent would resume the same ruling on
every pass, forever.

**`requestApproval` answers rather than asks, on a resumed Run.** It is the same call the worked example
gives the model, and on a Run whose Gate has been decided it reports the decision and the note instead of
raising a second elicitation. That is what makes one call serve both "ask" and "read the answer", and it is
why the runtime needs nothing else.

**`active` now means two things, and the resume path is explicit about which.** A Run somebody is driving,
and a Run whose Gate was just answered and which nobody is driving. `workRun` takes the ruling as an argument
and requires `active` when it has one and `pending` when it does not, so the two cannot be confused by
accident.

**A resumed Run gets a fresh session, and the prompt is three sentences.** What happened while it was
stopped, the note if there was one, and what to do about it. Everything else — how to work an Issue at all —
is the instructions every session carries, and the Issue, its Documents and the Run's own feed are read back
from deevy. That is the decision above about deevy being the memory, paying for itself: the ruling can land
while the service is stopped and the first pass after it starts picks the Run up.

## Slice 8: A webhook wakes it (M)

**Goal.** Work starts when it arrives rather than when the interval comes round, and the signature deevy
writes is verified by something deevy did not write.

**Depends on.** 4.

**Work.**

- An HTTP listener on the service: deevy's Agent webhook URL points at it, and a delivery it accepts nudges
  the loop to run a pass now instead of at the next interval. It dispatches nothing anywhere else — with the
  runtime a long-running service rather than a CI job, waking the thing that is already up is the whole job,
  and it means the receiver holds no second credential.
- Verification exactly as `docs/OPERATIONS.md` documents it: `t=<unix seconds>,v1=<hex>` over
  `<seconds>.<raw body>`, HMAC-SHA256 with the subscription's secret, compared against the **bytes received**,
  refused outside a five-minute window. Written in this package against the documentation, not imported from
  `packages/core` — convention 19 forbids the import and the forbidding is the point: this is the first time
  anything verifies a deevy signature that did not also produce it, and a cross-implementation test is worth
  more than a shared function.
- Dedupe on `deevy-delivery`, which every retry of an Event carries unchanged, so a redelivery is one wake.
- The wake carries no authority. It is a hint that there may be work; the pass that follows re-reads
  `runs.list` and decides for itself. A body that lies costs one wasted poll, which is the correct blast
  radius for an endpoint on the public internet.
- Polling stays on. The receiver is an accelerator, and a runtime that only worked when a webhook arrived
  would lose a Run to every missed delivery.

**Acceptance test.** Runtime: a body signed by `packages/core`'s own signer, in a devDependency test, is
accepted and wakes exactly one pass — the cross-implementation test, and the one that would have caught a
misreading of the documented scheme. A body whose signature is right for different bytes is refused; a
re-serialised body with the same JSON is refused, which is the mistake the docs warn about. A timestamp six
minutes old is refused even with a valid signature. The same `deevy-delivery` twice wakes once. A wake while
a pass is running does not start a second one. A wake with nothing to do is a no-op. End to end, against a
real deevy: assigning an Issue to the Agent delivers a `run.started` webhook that the service accepts, and
the Run is worked without waiting out a poll interval.

### Found by building the slice

**The receiver is the strongest test in M4 of something other than M4.** deevy signs, and something that has
never seen `packages/core`'s code verifies — including the two mistakes `OPERATIONS.md` warns about, a body
re-serialised from its own JSON and a signature moved forward in time. That check is only possible because
convention 19 forbids the import, which is the clearest return the boundary rule has paid.

**A wake ends a wait and nothing else.** It aborts a signal the loop makes fresh before each sleep, so it can
never interrupt a pass, start a second one, or race a stop. The loop is still a sequential while-loop and the
webhook only changes when the next iteration begins.

**The listener came with a health endpoint, which the container wanted anyway.** `GET /healthz` answers
whether or not a webhook secret is configured, so `docker compose` can tell whether the runtime is alive —
something slice 4 had no way to express and left out.

**No new dependency.** `node:http` reads the body as bytes and verifies the string they decode to, never
re-serialising it, which is exactly what the documented scheme requires. Reaching for a framework would have
made the one rule that matters harder to keep, not easier.

## Slice 9: Docs for the runtime and both targets (S)

**Goal.** PLAN.md's other half — "operator docs for both targets" — finished, with the runtime in them.

**Depends on.** 4 through 8.

**Work.**

- `docs/OPERATIONS.md` gains a runtime section: what the service is, the Agent and key it needs, the
  repository and git credential, the webhook subscription pointing at its listener, and its rows in the
  configuration table M3 built, in that table's columns. The Cloudflare and Docker sections gain the two
  sentences each that say how a runtime reaches them, which is the only difference between the targets from
  the runtime's side and worth saying because it is so nearly nothing.
- The safety section, plainly: Issue text is written by anyone with Project access and reaches a session with
  a shell; the container is the boundary; the credential is scoped; a laptop running the loop directly has no
  boundary at all. What is bounded, what is not, and which Gate is the last line.
- What it costs to run: which knobs move token spend — the model, the effort, the per-Run timeout, whether
  the repository is cloned per Run — stated as a table without inventing numbers nobody has measured.
- `docs/DEVELOPMENT.md`: running the runtime against `vp run -r --parallel dev`, the seeded Agent, and how to
  drive a Run with the scripted session so a developer can work on it without a key.
- [agent-loop.md](../agent-loop.md) is re-pointed rather than rewritten. Its worked example of a person's
  `claude` CLI configuration stays true and stays useful; it gains a header saying the shipped runtime is
  `apps/claude-agent`, and its `CLAUDE.md` snippet gains a line naming `src/instructions.md` as the original.

**Acceptance test.** Docs: every environment variable the runtime reads appears in the configuration table,
asserted by a test that reads `readConfig`'s schema and greps the table — the same mechanical check M3 wanted
for `run_worker_first` and for the same reason. Every command in the new sections runs as written against a
fresh checkout. A person who has not seen this repository follows the runtime section and gets a Run worked;
that one is a walk, not a test, and slice 10 is where it happens.

### Found by building the slice

**The mechanical check found its first bug in the test that wrote it.** Reading `env.NAME` out of
`config.ts` misses the two variables the runtime cannot start without, because those are read through a
`required(env, "NAME")` helper and are string literals. Matching every `DEEVY_*` name in the file finds all
of them — and the table has to be scoped to its own section, or deevy's own configuration rows in the same
document are read as the runtime's. Deliberately adding an undocumented knob was run, and the test failed on
it.

**One knob the check can never see, and it is the important one.** `ANTHROPIC_API_KEY` is read by the Agent
SDK rather than by `readConfig`, and a runtime without it fails every session. It has its own assertion,
because a mechanical check that only knows about the code cannot know about a dependency's environment.

**The cost section has no numbers, and says so.** Nothing here has been measured. Naming which knobs move the
bill and in which direction is honest; inventing a figure per Run would not be, and an operator who planned
against it would be worse off than one who was told to watch.

**The safety section is a list of what each bound actually does**, not a reassurance. It ends by naming what
is _not_ bounded — a session with a shell runs whatever the repository's build runs, reaches the network, and
spends tokens — because a section that only lists mitigations reads as a claim that the problem is solved.

## Slice 10: M4 release, v1 (M)

**Goal.** v1, from a tag, with the plan corrected to what shipped.

**Depends on.** 1 through 9.

**Work.**

- PLAN.md's M4 paragraph rewritten to what exists: an Agent SDK service rather than Claude Code headless in a
  GitHub Action, a webhook receiver that wakes it rather than one that dispatches to CI, and the local loop
  as promised. The stale sentences about M3 go with it — CLAUDE.md's "not yet run against a Cloudflare
  account" and PLAN.md's matching line are wrong, because the runbook was walked and the account torn down
  afterwards, and `m3-acceptance.md` records the result.
- `README.md`'s status becomes v1. `CLAUDE.md`'s current milestone follows.
- Two ADRs. **The reference runtime is a service, not a CI job**, recording the billing and Gate-latency
  reasoning above and what it costs — no per-Run isolation for free, a host somebody has to run. **An Agent's
  input is untrusted and its tools are not**, recording that Issue text authored by anyone with Project
  access reaches a session holding a shell, and that the bound is the container, the allowlist, the scoped
  credential and the Gate — because a decision that is only in a doc section gets refactored away by somebody
  who never read it.
- `release.yml` accepts `v0.4.*`, and the slice decides whether the runtime image is published beside deevy's
  or documented as a build — publishing an image that runs an agent against a repository is a choice with
  consequences, and it gets made deliberately here rather than inherited from a copied job block.

**Acceptance test.** The whole scenario, twice, from one tag, driven by the runtime rather than by a person.
On the Docker image: an admin signs in, creates the `planner` Agent, grants it the Project, issues a key, and
points the runtime at both. An Issue with an intent Document is assigned. The service picks it up without
being told twice, narrates as it works, writes the plan Document, reaches the Plan Gate and stops. The Human
gets the Notification, opens the link, sees the Gate focused beside the Document and the Activity feed, and
approves with a note. The service resumes, works the Build State in the checked-out repository, opens a pull
request, attaches its URL to the Run, and finishes with a summary naming both. The board updated itself
throughout without anyone reloading, and the Event log tells the whole story with the Agent as actor and the
Human one hop away. Then the same walk against a Cloudflare Worker built from the same commit, with the
runtime's only change being the URL it points at — because one codebase on two runtimes is the claim
ADR-0006 makes, and a client that cannot tell them apart is the strongest evidence for it anyone has
produced yet.

It is [sockets-acceptance.md](../sockets-acceptance.md), and it is **a script that has been run**:
`vp run claude-agent#acceptance` walks both deployments on one machine with no Cloudflare account, no GitHub
OAuth App and no repository on the internet, and CI runs it on every commit. Twenty-nine checks pass. The one
thing it cannot stand in for is Claude itself, which is the live test, and that has not been run.

### Found by building the slice

**Two images, one tag, and the second one is a decision rather than a copied job block.** Publishing an image
that runs an agent against a repository is not the same act as publishing deevy, so `publish-agent` says why
it exists in a comment, `docker-compose.yml` keeps the runtime behind a `--profile agent` and points at
ADR-0014, and both images come from the same verified commit.

**PLAN.md's M3 paragraph was wrong in the other direction.** It said the acceptance walk had not been run
against a Cloudflare account. It had — `m3-acceptance.md` records it, on 2026-09-04 and 2026-09-05 — and
CLAUDE.md carried the same stale sentence. Corrected here, and M4's own status line says plainly that its
walk has not been run.

**The walk had to stop needing an account before it was worth writing.** The first version of this slice
produced a runbook that needed a Cloudflare account, a GitHub OAuth App, a repository on the internet and an
Anthropic key — four reasons never to run it, and it was not run. Everything but the last is already
stubbed somewhere in this repository: `wrangler dev --local` is a real Worker on a real local D1,
`apps/web/scripts/stub-github.js` is the OAuth dance with only the far end replaced, `git` needs nothing but a
directory, and GitHub's pull-request endpoint is thirty lines of `node:http`. So the walk became a script that
runs on every commit, and the only thing left outside it is the model.

That cost two knobs — `DEEVY_AGENT_GITHUB_API` and `DEEVY_AGENT_GITHUB_REPO` — which are not test
scaffolding: they are what GitHub Enterprise needs too, and the clone URL is not always the whole story.

**The two deployments produce byte-identical Event logs, and the script compares them.** That is ADR-0006's
claim stated as an assertion rather than as prose, and it is the strongest form of it the project has: not
"both runtimes pass their tests" but "one client walked both and could not tell".

**Three assertions written from memory were wrong about deevy**, and each was worth finding: `run.started` is
attributed to the Human whose assignment triggered it, `run.answered` to the Human whose ruling reached the
Run, and the story carries `document.updated`, `issue.link_added` and `comment.created` too. The Event log
says more than the plan credited it with.

**The ADRs record two different kinds of thing, and both needed writing down.** ADR-0013 is a deviation from
a plan sentence, with the cost stated: somebody has to run a host, and per-Run isolation is the runtime's own
rather than a fresh machine's. ADR-0014 is a standing position with a rule for what comes next — a capability
an agent gets must come with what stops it reaching further and what a Human sees when it tries. The second
one exists because everything it describes is otherwise spread across a `sessionOptions` object, an `env`
filter and four `disallowedTools` entries that a later refactor would quietly undo.
