# M2 Agents: vertical slices

Breakdown of the M2 milestone from [PLAN.md](../PLAN.md), 2026-09-04. Vocabulary is
[CONTEXT.md](../../CONTEXT.md); M1's slices are in [m1.md](./m1.md). M2 is done when a Claude Code loop
outside deevy picks up an assigned Issue, writes a plan Document, hits the Plan Gate, and resumes after a
Human approves in deevy.

Nine slices, in dependency order. Each is one PR on `main` that leaves the image deployable, adds its
operations to the registry, and carries its own tests. Nothing in a slice is needed by an earlier one.

## Decisions taken for M2

- **Agents are default-denied.** `OperationMeta` gains `agents?: true`, orthogonal to the existing
  `public | session | member | admin` ladder. An Agent Member is refused every operation that does not opt
  in, so the forty Human-only operations are edited zero times and every operation added after M2 is
  agent-denied until someone thinks about it. A conditional type makes `agents` unsayable on an `admin`
  operation, so ADR-0004 is a compile error rather than a test.
- **`sessionOnly?: true` on Gate decisions.** `assertHuman` checks `member.kind`, which does not stop a
  Human's own MCP client from approving on their behalf once slice 7 mints OAuth tokens. `gates.approve` and
  `gates.reject` require a cookie principal: approval happens in deevy's UI, in a browser, or not at all.
  This rule is not in ADR-0004 and is worth an ADR amendment in slice 9.
- **Agents are scoped to granted Projects** (PLAN.md). An ungranted Project is `NOT_FOUND` to an Agent, not
  `FORBIDDEN`. The check lives at the two choke points that already load the Project row, `requireProject`
  and `requireIssue`, not in the middleware: the project id is derived inside the handler, and a middleware
  resolver would either re-query or need one bespoke resolver per operation. It is the same seam private
  Projects will use after v1.
- **Agents may create Labels and set them on Issues, never update or delete them.** Labels are
  Workspace-scoped, so a granted Agent deleting one reaches Projects it cannot see.
- **Assigning an Issue to an Agent makes it the Assignee outright.** No separate delegate concept (Linear
  splits them; we do not, and CONTEXT.md says an Issue has at most one Assignee).
- **The MCP tool list is opt-in**, a third meta field `mcp?: true`, independent of `agents`. Authorization
  and surface are different questions, and a seventy-tool list poisons an agent's context window. The list
  is snapshotted to `packages/core/mcp-tools.json` and diffed in CI exactly like `openapi.json` (ADR-0009).
- **One authorization path, three surfaces.** An MCP tool call invokes the same procedure through
  `call(procedure, input, { context })`, so `authorize()`, the agent rule, and the grant check all run once
  and in one place. Filtering `tools/list` per principal is display only and never the enforcement.
- **No `requireMcpAuth`.** It self-fetches `/jwks` and fails when the authorization server and the resource
  server are one process (better-auth#10888). Use `verifyJwsAccessToken` with an in-process `jwksFetch` that
  dispatches into `auth.handler`, which is web-standard and works unchanged on Workers in M3.
- **Background work: ports in core, timer in the adapter, runner in `apps/server`.** `createApp` must not
  start a timer, because `apps/web/src/worker.ts` calls it per request. Every unit of background work is a
  bounded function of `(db, now, fetch, limit)`: one indexed SELECT with a LIMIT, one batched UPDATE, no
  per-row query, so M3's Cron Trigger fits inside Cloudflare's 10 ms CPU budget.
- **Webhook retries derive from the Event log** (ADR-0003) by inserting a `webhook_delivery` row in
  `appendEvent`'s tail, beside `deriveNotifications`. The durable row is the record; the job queue is only a
  hint, so a dead timer loses nothing.
- **The Run lifecycle matches the shape Linear and Plane converged on**, so existing agents port with a thin
  adapter: `pending` to `active` to `awaiting_input` and back to `active`, ending `completed` or `failed`,
  with `stale` after 30 minutes of silence. `stale` is recoverable, never terminal.
- **A schedule on an Agent creates one Run per Issue assigned to it that has no open Run.** PLAN.md names the
  trigger but not its subject; this is the useful reading, and it needs no new "what does it run on" concept.
- **OAuth tokens are full-session-equivalent in v1.** Scopes ride on the principal but nothing enforces them;
  narrowing later is a middleware change, not a context change.

## Deferred out of M2

Agent-to-agent delegation through sub-issues; cost and time accounting per Run; the Slack app with per-person
DMs and approve buttons (M2 is incoming webhooks only); email Channel; four-eyes Gates;
requester-cannot-approve; private Projects; MCP `subscriptions/listen` (needs a shared bus, ADR-0006) and the
tasks extension (agents are external, ADR-0003); the reference agent runtime (M4); per-Agent rate limits
beyond the edge.

GitLab, Google and OIDC sign-in were on this list too, deferred out of M1 before it; they were built after v1
in [sign-in.md](./sign-in.md).

## Conventions every slice follows

M1's eight-step definition of done ([m1.md](./m1.md)) holds unchanged. M2 adds five rules:

9. A Better Auth plugin change lives twice: `packages/core/src/auth.ts` and
   `packages/db/auth.generate.config.ts`. Change both, run `vp run db#generate:auth`, then `vp run
db#generate` and `vp run db#check:migrations`. Never hand-edit `packages/db/src/schema/auth.ts`.
10. Every new operation states `agents` and `mcp` deliberately. Omission is denial, and that is the point.
11. `vp run core#snapshot:mcp-tools` committed alongside `core#snapshot:openapi`; CI fails on either being
    stale (ADR-0009).
12. Crypto in `packages/core` is `crypto.subtle`, never `node:crypto` (ADR-0006). The Workers build catches
    the leak.
13. Background work is a bounded function in `packages/core/src/work.ts` invoked through a port. No timer, no
    `setInterval`, and no unbounded scan in `packages/core`.
14. Dependencies change in one place at a time. The catalog, the lockfile and the migrations folder are
    whole-tree artifacts: two slices built in parallel may not both touch them, and `vp install` is the only
    way to install (bare `pnpm` picks up whatever the shell pins and cannot read the pnpm 11 lockfile).

Sizes are t-shirt estimates for one developer plus agents: S under a day, M two to three days, L a week.

## Dependency order

```
M1
└─ 1 Agents, Sponsors, and API keys
   └─ 2 Runs and Activities              brings the job and cron ports, and the stale sweep
      ├─ 3 MCP server and the v1 tool set
      │  ├─ 6 Gate approval by URL elicitation
      │  └─ 7 OAuth authorization server for Human MCP clients
      ├─ 4 Triggers
      │  └─ 5 Signed webhooks with retries
      └─ 8 Slack Channels and routing     parallel with 3 to 7 from the day 2 lands
         9 M2 release: the agent loop     needs everything
```

Slice 8 depends only on M1's Event log plus slice 2's Run Notification kinds, so it can be handed to someone
else on day one of slice 3. Slice 7 is deliberately late: it is the highest-churn dependency in the tree (four
open CIMD and DCR interop bugs upstream, filed in the last month) and M2's definition of done does not need
it, so a week of chasing upstream cannot block the milestone.

## Slice 1: Agents, Sponsors, and API keys (L)

**Goal.** A Sponsor creates an Agent, issues it a key, and the Agent reaches the same API a Human uses, with
a capability set it cannot exceed and a set of Projects it cannot see past.

**Depends on.** M1.

**Schema.** The `apikey` table arrives from `@better-auth/api-key` through `vp run db#generate:auth`.
`member.sponsorId` gains its self-referencing foreign key (the column exists, unused, since M1).
`agent`: `memberId` primary key referencing `member`, `webhookUrl` nullable, `webhookSecret` nullable,
`scheduleMinutes` integer nullable (slice 4 uses it; the column lands now so slices 4 and 5 do not migrate
the same table twice), `createdAt`. `project_grant`: `(memberId, projectId)` primary key, `grantedBy`,
`createdAt`, index on `projectId`.

**Core.**

- `createAuth` gains `plugins: [apiKey({ ... })]` with a custom getter that reads
  `Authorization: Bearer deevy_sk_…`. The plugin's default header is `x-api-key`, and MCP clients send
  bearer. Rate limiting off: it would silently 429 an agent loop, so rate-limit at the edge.
- New `packages/core/src/principal.ts`:
  `Principal = { kind: "anonymous" } | { kind: "cookie" } | { kind: "api_key"; keyId } | { kind: "oauth";
clientId; scopes }`, and `resolvePrincipal({ auth, headers, jwksFetch? })`. Three arms, in order: a bearer
  with the deevy key prefix, a bearer without it (slice 7 fills this in; the signature exists now), then the
  cookie. The prefix discriminator matters: an Agent's key and a Human's access token arrive on the same
  header at the same endpoint.
- `buildContext` in `app.ts` calls `resolvePrincipal`, then the existing Member lookup, then resolves
  `grantedProjectIds` for an agent principal only (one extra query, agents only).
- `AppContext` gains `principal: Principal` and `grantedProjectIds: string[] | null` (`null` means every
  Project: a Human is not scoped in v1).
- Registry: `agents?: true` and `sessionOnly?: true` on `OperationMeta`, a conditional type so `agents` is
  only sayable on a `member` operation, and `authorize(meta)` gaining two checks. Neither field touches the
  `openapi()` meta, so `openapi.json` does not churn.
- `assertProjectVisible(context, projectId)` called from `requireProject` and `requireIssue`; direct filters
  on `projects.list`, `events.list` (which also excludes Events with a null `projectId` for agents) and
  `inbox.list`.
- Sponsor cascade (PLAN.md): suspending a Human sets `suspendedAt` on the Agents it sponsors and appends one
  `member.suspended` per Agent; reinstating reverses it; giving an Agent an active Sponsor lifts it.
- `gates.approve` and `gates.reject` gain `sessionOnly: true`.
- `tests/helpers.ts` gains `agentContext(db, { sponsor, grants })`.

**Operations.** `agents.list`, `agents.create` (member: any Human may sponsor an Agent and becomes its
Sponsor), `agents.update` (Sponsor or admin: name, handle, webhook URL), `agents.setSponsor` (admin),
`agents.suspend`, `agents.reinstate` (Sponsor or admin), `agents.keys.list`, `agents.keys.issue` (returns the
plaintext key once), `agents.keys.revoke`, `agents.grants.list`, `agents.grants.add`, `agents.grants.remove`.
Events: `agent.created`, `agent.updated`, `agent.key_issued`, `agent.key_revoked`, `agent.sponsor_changed`,
`agent.project_granted`, `agent.project_revoked`; suspension reuses `member.suspended` and
`member.reinstated`.

Roughly fifteen existing operations gain `agents: true`: `issues.list/get/create/update/move/setLabels`,
`documents.list/get/write`, `comments.list/create`, `labels.list/create`, `links.list/add`, `inbox.list`.

**UI.** `/settings/agents`: the Agent list with Sponsor and status, a create dialog (name, handle), and a
detail page with API keys (the plaintext shown exactly once, with a copy button and a warning), Project
grants, the webhook URL, and Suspend. Agent Members appear in Assignee and mention pickers with a badge.

**Spike, inside this slice's week.** Mount a hello-world `createMcpHandler` in `apps/web/src/worker.ts` and
run `vp run web#build:workers` to prove `@modelcontextprotocol/server` 2.0.0 has no `node:` import. If it
does, the whole projection moves to `packages/adapters` and slice 3 changes shape. Separately, try CIMD
against Better Auth 1.7.2 to learn early whether slice 7 is a day or a week.

**Spike result, 2026-09-04.** `@modelcontextprotocol/server` 2.0.0 satisfies ADR-0006, so slice 3 keeps its
shape and stays in `packages/core`. Its main entry exports `createMcpHandler`, `McpServer`, `inputRequired`
and `createRequestStateCodec`, and reaches `node:` only through the `_shims` subpath, whose export map
carries a `workerd` condition resolving to a shim with no `node:` import at all; `node:stream` and
`node:process` appear only in the stdio transport and the Node shim, neither of which the main entry reaches
on workerd. The residual risk is therefore narrow and testable: the bundler must honour the `workerd` export
condition. `@modelcontextprotocol/hono` 2.0.0, `@better-auth/api-key`, `@better-auth/mcp` and
`@better-auth/cimd` 1.7.2 all exist at the pinned line.

**Acceptance test.** Core: a Human creates an Agent, whose Member has `kind = "agent"` and `sponsorId` the
creator; `agents.keys.issue` returns a plaintext key once and never again; a request carrying it as
`Authorization: Bearer deevy_sk_…` resolves to that Member with `principal.kind = "api_key"`; that Agent gets
`FORBIDDEN` on `projects.create`, `allowlist.add`, `members.list`, `labels.delete` and `gates.approve`, and
succeeds on `issues.get` for a granted Project; an Issue in an ungranted Project is `NOT_FOUND` and
`projects.list` returns only granted Projects; a request carrying an invalid bearer _and_ a valid cookie is
`UNAUTHORIZED`, not the cookie Human; `gates.approve` from a non-cookie principal is `FORBIDDEN` even when
the Member is a Human; suspending the Sponsor makes the Agent's key fail with "Not a Member of this
Workspace". A table-driven test calls every `agents: true` operation against an ungranted Project and expects
`NOT_FOUND`. SPA: `/settings/agents` renders from a mocked client and shows an issued key exactly once.
Manual: `curl -H "Authorization: Bearer …" localhost:3000/api/issues/DEV-1`. Workers build green.

## Slice 2: Runs and Activities (L)

**Goal.** An Agent's attempt on an Issue is a first-class record with a lifecycle, and a Run that goes silent
goes `stale` on its own.

**Depends on.** 1.

**Schema.** `run`: `id`, `issueId`, `agentMemberId`, `triggeredByMemberId` nullable, `trigger`
(`assignment | mention | state_rule | schedule | manual`), `status`
(`pending | active | awaiting_input | completed | failed | stale`), `summary` nullable, `startedAt` nullable,
`lastActivityAt`, `finishedAt` nullable, `createdAt`. Indexes `(issueId, createdAt)`,
`(agentMemberId, status)`, and `(status, lastActivityAt)` for the sweep. `activity`: `id`, `runId`, `kind`
(`thought | action | elicitation | response | error`), `body`, `payload` JSON nullable, `createdAt`, index
`(runId, createdAt)`. `issue_link` gains `runId` nullable, so evidence a Run attaches is attributed to it.
`notificationKinds` gains `run_awaiting_input` and `run_finished` (PLAN.md names five kinds; M1 shipped
three).

**Core.**

- `packages/core/src/runs.ts`: the transition table and one `assertTransition`. `pending` becomes `active` on
  the first Activity; any `elicitation` Activity moves to `awaiting_input`; a Human's answer returns it to
  `active`; `runs.finish` moves to `completed` or `failed`; the sweep moves a silent Run to `stale`, and any
  further Activity returns it to `active`. At most one open Run per `(issue, agent)`.
- `packages/core/src/jobs.ts`: the ports, web-standard.
  `JobQueue { enqueue(job: { kind, id, delaySeconds? }): Promise<void> }`, whose enqueue never throws into a
  request because the durable row is the record. `Cron { every(seconds, run: (signal) => Promise<void>):
() => void }`, returning its stop function.
- `packages/core/src/work.ts`: `sweepStaleRuns({ db, workspaceId, now, limit = 50, silenceMs })` returning
  `{ scanned, changed, more }`: one indexed SELECT with a LIMIT, one `UPDATE … WHERE id IN (…)`, one
  multi-row Event insert. `more: true` means run again rather than raise the limit.
- `packages/adapters/src/node/cron.ts`: `createTimerCron()`. `apps/server/src/runner.ts`:
  `startRunner({ db, cron, … })` started beside `serve()` and stopped on SIGTERM. The wiring stays in
  `apps/server` because `@deevy/core` already dev-depends on `@deevy/adapters`, and an adapters-to-core edge
  would close the cycle.
- `deriveNotifications` gains: `run.awaiting_input` notifies the triggering Human, or the Agent's Sponsor when
  an Agent triggered it; `run.completed` and `run.failed` notify the same Human.

**Operations.** `runs.start`, `runs.postActivity`, `runs.finish` (member, `agents: true`, an Agent only on its
own Runs); `runs.list` (by Issue or Agent), `runs.get` (member); `runs.answer` (member, Human, answers an
elicitation). `links.add` accepts an optional `runId`. Events: `run.started` (trigger in the payload),
`run.activity`, `run.awaiting_input`, `run.answered`, `run.completed`, `run.failed`, `run.went_stale`.

**Env.** `DEEVY_RUN_STALE_MINUTES` (default 30), `DEEVY_SWEEP_INTERVAL_SECONDS` (default 60).

**UI.** Issue page Runs section: one collapsible block per Run with status badge, Agent, trigger and elapsed
time; the Activity feed with `thought` and `action` collapsed by default and `response` and `error`
prominent; attached evidence Links; and an Answer box while `awaiting_input`. Live through `useLiveEvents`.

**Acceptance test.** Core: an Agent calls `runs.start` on a granted Issue and gets `pending`; a `thought`
Activity moves it to `active`; an `elicitation` moves it to `awaiting_input` and gives the triggering Human
one `run_awaiting_input` Notification; `runs.answer` returns it to `active`; `runs.finish` with
`status: "completed"` and a summary gives one `run_finished` Notification; an Agent posting to another
Agent's Run is `FORBIDDEN`; a Run whose `lastActivityAt` is 31 minutes old becomes `stale` with a
`run.went_stale` Event, and a further Activity returns it to `active`; `sweepStaleRuns` over 50 due Runs
issues a fixed, asserted number of statements and returns `more: true` at the limit. Node: `startRunner`
starts and stops with no leaked timer (the test fails if the process will not exit). SPA: the Runs section
renders from a mocked client with an Answer box on `awaiting_input`.

## Slice 3: MCP server and the v1 tool set (L)

**Goal.** An Agent works an Issue over MCP: reads it, writes its Documents, comments, and drives its Run.

**Depends on.** 2.

**Schema.** None.

**Core.**

- Registry gains `mcp?: true`.
- `packages/core/src/mcp/tools.ts`: `projectTools(router): ToolDescriptor[]`, walking the plain router object
  (`instanceof Procedure`; oRPC 2.0 beta has no `isProcedure`), reading `getOperationMeta`, keeping
  `mcp: true`, deriving the tool name by replacing `.` with `_` (`issues.get` becomes `issues_get`), and
  asserting the mapping stays injective. Every access to `procedure['~orpc'].inputSchemas` is isolated in one
  `schemasOf()` function, because it is private and a beta bump can rename it. Pure, no I/O, so the CI
  snapshot calls it directly.
- `packages/core/src/mcp/server.ts`: `createDeevyMcp({ db, auth, baseURL })` on
  `createMcpHandler(factory, { responseMode: "auto", legacy: "stateless" })`, a fresh `McpServer` per request
  (ADR-0005: no protocol sessions, so any instance answers any request). The tool callback builds an
  `AppContext` from `authInfo` and invokes `call(procedure, input, { context })`, so `authorize()`, the agent
  rule and `assertProjectVisible` all run untouched. `ORPCError` becomes a tool error carrying its message.
- `tools/list` is pre-filtered per principal, so an Agent does not see tools it cannot call. Display only.
- `app.ts` mounts `app.all("/mcp", …)` before the oRPC handlers. An unauthenticated request is 401 with
  `WWW-Authenticate: Bearer resource_metadata="<base>/.well-known/oauth-protected-resource"` (RFC 9728),
  which is what makes a client start the OAuth dance in slice 7 instead of simply failing.
- The Vite dev proxy gains `/mcp` and `/.well-known` next to `/api`, `/rpc`, `/healthz`.

**Operations.** No new ones. `mcp: true` goes on PLAN.md's v1 set: `issues.list`, `issues.get`,
`issues.create`, `issues.update`, `documents.get`, `documents.write`, `comments.create`, `labels.list`,
`issues.setLabels`, `links.add`, `inbox.list`, `runs.start`, `runs.postActivity`, `runs.finish`.

**CI.** `packages/core/scripts/snapshot-mcp-tools.ts` writes `packages/core/mcp-tools.json` (name, operation,
summary, readOnly, agents, inputSchema, using the same `ZodToJsonSchemaConverter` as `openapi.ts`), and CI
gains a step that regenerates it and runs `git diff --exit-code`, beside the existing OpenAPI step (ADR-0009).

**UI.** The `/settings/agents` detail page shows the MCP endpoint URL and a ready-to-paste `claude mcp add`
command for that Agent.

**Acceptance test.** Core: `projectTools(router)` matches `mcp-tools.json` exactly; every tool name is unique
and matches `^[a-z]+(_[a-z]+)+$`; a tool call authenticated with an Agent's key reads `DEV-1` and writes its
plan Document; the same call for an ungranted Project returns a tool error saying "No such Project";
`gates_approve` is absent from `tools/list` and refused if called by name. A request in the SDK's
`legacy: "stateless"` mode from a 2025-11-25 client succeeds (Cursor and VS Code are a named PLAN.md risk).
An unauthenticated POST to `/mcp` is 401 carrying the `WWW-Authenticate` header. Manual:
`claude mcp add --transport http deevy http://localhost:3000/mcp --header "Authorization: Bearer …"`, then
Claude Code lists the tools and reads an Issue. Workers build green.

## Slice 4: Triggers (M)

**Goal.** All four triggers from PLAN.md create a Run in `pending`.

**Depends on.** 2. (3 makes it visible to a real agent, but the triggers are surface-independent.)

**Schema.** `workflow_state` gains `triggerAgentMemberId` nullable: the rule that fires on entering the State.
`agent.scheduleMinutes` already exists from slice 1.

**Core.** `packages/core/src/triggers.ts`: `triggersFor(event)` runs in `appendEvent`'s tail beside
`deriveNotifications`. Rules: `issue.assigned` whose new Assignee is an Agent creates a Run with
`trigger: "assignment"`; `comment.created` whose `mentionedMemberIds` include an Agent creates a `mention`
Run; entering a State carrying `triggerAgentMemberId` assigns the Issue to that Agent and creates a
`state_rule` Run. `work.ts` gains `sweepSchedules`, driven by the same `Cron` as the stale sweep: each Agent
whose `scheduleMinutes` is due gets one Run per assigned Issue with no open Run. Every path is guarded by the
"at most one open Run per `(issue, agent)`" rule from slice 2, so nothing double-fires.

**Operations.** `workflow.update` accepts `triggerAgentMemberId` per State; `agents.update` accepts
`scheduleMinutes`. Events: `run.started` carries `trigger`; the State rule rides on `workflow.updated`.

**UI.** The workflow editor gains an "assign an Agent on entering" picker per State; the Agent detail page
gains the schedule field; each Run on the Issue page shows what triggered it and who.

**Acceptance test.** Core: assigning `DEV-1` to an Agent creates exactly one `pending` Run with
`trigger = "assignment"`, and reassigning to the same Agent creates no second Run; a comment "ping @planner"
creates a `mention` Run; approving the Spec Gate lands `DEV-1` in Plan, whose rule names the planning Agent,
which assigns the Issue and creates a `state_rule` Run; an Agent with `scheduleMinutes = 60` and two assigned
Issues gets two Runs on the first sweep and none on the second; assigning to a Human creates no Run; a
mention of a Team containing an Agent creates one Run for that Agent.

## Slice 5: Signed webhooks with retries (M)

**Goal.** An Agent that registered a URL is told, reliably, from the Event log (ADR-0003).

**Depends on.** 4 (and 2 for the job port).

**Schema.** `webhook_subscription`: `id`, `workspaceId`, `memberId` nullable (the Agent; null is a generic
subscriber), `url`, `secret`, `kinds` JSON nullable (null is all), `projectId` nullable, `createdBy`,
`createdAt`, `disabledAt` nullable. `webhook_delivery`: `id`, `subscriptionId`, `eventSeq`, `attempts`
default 0, `nextAttemptAt`, `lockedUntil` nullable, `lastStatus` nullable, `lastError` nullable,
`deliveredAt` nullable; unique `(subscriptionId, eventSeq)`, index on `nextAttemptAt` for undelivered rows.

**Core.** `appendEvent` inserts every matching delivery in one multi-row statement, next to
`deriveNotifications`, so nothing is lost if the timer dies and no queue is needed for correctness.
`packages/core/src/webhooks.ts`: `signPayload(secret, timestamp, body)` with `crypto.subtle` HMAC-SHA256,
header `deevy-signature: t=<unix>,v1=<hex>`, five-minute replay window. `work.ts` gains
`deliverDueWebhooks(options)` and `deliverWebhook({ deliveryId })`, the single-message form an M3 Queue
consumer drives. Claiming without transactions, which D1 does not have:
`UPDATE webhook_delivery SET lockedUntil = :now+60s WHERE id IN (…) AND (lockedUntil IS NULL OR lockedUntil <
:now) RETURNING id`, taking only the returned ids. Backoff `min(2^attempts × 10s, 6h)` with jitter, eight
attempts, then `webhook.exhausted`. The Node `JobQueue` implementation is honestly a wake-up that shortens
the next tick; the interface exists because M3 replaces it wholesale with Queues.

**Operations.** `webhooks.list`, `webhooks.create`, `webhooks.update`, `webhooks.delete` (admin, or the
Sponsor for their own Agent's URL), `webhooks.deliveries` (recent attempts for a subscription),
`webhooks.redeliver`. Events: `webhook.subscribed`, `webhook.removed`, `webhook.exhausted`.

**UI.** `/settings/webhooks`: subscriptions with their event-kind filter, and the last deliveries with status
and error. The Agent detail page shows its own URL with a Test button.

**Acceptance test.** Core with a stubbed fetch: creating an Issue in a subscribed Project inserts exactly one
delivery; `deliverWebhook` POSTs a body whose `deevy-signature` verifies against the secret and whose
timestamp is inside the window; a 500 sets `attempts = 1` and `nextAttemptAt` about ten seconds out; the
eighth failure appends `webhook.exhausted` and stops; a 200 marks it delivered and never retries; two
concurrent `deliverDueWebhooks` calls claim disjoint sets; a subscription filtered to `run.*` receives no
`issue.updated`. Manual: point a subscription at a local receiver and watch an assignment arrive signed.

### Correction found while building slice 5

Slice 1 put `webhookUrl` and `webhookSecret` on the `agent` row, on the plan's own instruction that the column
should land early "so slice 5 doesn't migrate the same table twice". Slice 5 then built
`webhook_subscription`, which carries a URL, a secret, a kind filter, a Project scope and a disabled flag, and
made it the only thing delivery reads. The two now disagree: a Sponsor who sets an Agent's URL on the Agents
page is told it is saved and nothing is ever delivered to it.

The subscription is authoritative, because it is the shape the feature actually needs. `agents.update` keeps
taking a `webhookUrl` — the Sponsor should set it where the Agent is, not on a separate page — but writes a
subscription scoped to that Agent, `AgentSchema.webhookUrl` reads it back, and the two dead columns go. The
lesson for the rest of the milestone is that putting a column in early to save a migration bought nothing and
cost a wrong feature: the migration is cheap, and guessing a shape a later slice has not designed yet is not.

## Slice 6: Gate approval by URL elicitation (M)

**Goal.** An Agent that reaches a Gate mid-Run hands the Human a deevy URL and resumes after the decision:
the second half of M2's definition of done.

**Depends on.** 3 and 2.

**Schema.** `gate_approver`: `(stateId, memberId)` primary key. Empty means any Human, which is M1's
behaviour ([m1.md](./m1.md) deferred named approvers to M2, "where Runs make them matter").

**Core.** `packages/core/src/mcp/elicitation.ts`: `runs.requestApproval` returns MRTR
`inputRequired({ inputRequests: { approval: inputRequired.elicitUrl({ url }) }, requestState })` with
`createRequestStateCodec({ key: env.secret, ttlSeconds })`, the URL being
`<baseURL>/issues/DEV-42?gate=<stateId>`. On the client's retry the server checks the `gate_decision` row for
that `(issue, state)`; the `requestState` only binds the retry to the same principal, which the 2026-07-28
revision requires ("the server MUST verify the same user completes it"). An explicit tool rather than an
implicit failure on `issues.move`, so a polling Agent with no elicitation support sees the same thing: the
Run goes `awaiting_input` with an `elicitation` Activity carrying the URL. `deriveNotifications`' Gate rule
narrows to the named approvers when a State has any, and stays "every active Human" when it does not.

**Operations.** `runs.requestApproval` (member, `agents: true`, `mcp: true`); `workflow.update` accepts
`approverMemberIds` per State. Events: reuse `run.awaiting_input`; `workflow.updated` covers the approvers.

**UI.** The Issue page highlights and scrolls to the Gate when `?gate=` is present. The workflow editor gains
an approvers picker per Gate State. The Run block shows "waiting for approval" and, afterwards, who decided.

**Acceptance test.** Core: `runs.requestApproval` on an Issue in the Plan Gate puts the Run in
`awaiting_input`, writes an `elicitation` Activity whose payload carries the deevy URL, and notifies only the
named approvers; approving as one of them moves the Issue and returns the Run to `active`; a retry before any
decision returns `input_required` again; a `requestState` minted for a different principal is refused, and an
expired one is refused. MCP: a Claude Code session reaches the Plan Gate, the URL opens the Issue with the
Gate focused, and approval resumes the tool call. Browser: walk one Issue from Intent to Done with an Agent
doing the work and a Human deciding every Gate.

## Slice 7: OAuth authorization server for Human MCP clients (M)

**Goal.** A Human points their own MCP client at deevy and acts as themselves, not as an Agent.

**Depends on.** 3.

**Schema.** The OAuth application, access token, consent and JWKS tables arrive from `@better-auth/mcp` plus
the `jwt` plugin (and `@better-auth/cimd`) through `vp run db#generate:auth`. Mirror the plugin list in
`packages/db/auth.generate.config.ts`.

**Core.** The plugins go into `createAuth`. `resolvePrincipal`'s second arm is filled in:
`auth.api.verifyJwsAccessToken({ body: { token }, jwksFetch })` with
`jwksFetch = (input, init) => auth.handler(new Request(input, init))`: one line, web-standard, and the
workaround for better-auth#10888, which bites hardest on M3's single Worker. `requireMcpAuth` is never
called. RFC 9728 protected-resource metadata at `/.well-known/oauth-protected-resource` for the `/mcp`
resource; RFC 8414 authorization-server metadata from the plugin; PKCE S256 enforced; RFC 8707 `resource`
required and its audience validated; CIMD on, DCR opt-in for legacy clients only (it is deprecated in the
2026-07-28 revision). `sessionOnly` from slice 1 is what keeps `gates.approve` in the browser.

**Settled in slice 3, and binding here.** RFC 9728 builds a resource's metadata URL by inserting the
well-known segment between the host and the resource's own path, so the document for the endpoint at `/mcp`
belongs at `/.well-known/oauth-protected-resource/mcp`, which is what slice 3's 401 challenge already
advertises and what a client that derives the URL rather than reading the header will fetch. Better Auth's
plugin serves the root form, `/.well-known/oauth-protected-resource`, so this slice has to reconcile the two:
serve the path-inserting form, and serve the root form as well if that costs a route.

**Operations.** `me.get` returns `principal.kind` so the SPA can say how the caller arrived.
`oauthClients.list` and `oauthClients.revoke` (session, the caller's own consents).

**UI.** The Better Auth consent page styled with shadcn. `/settings/mcp-clients` lists consented clients with
Revoke, and a "Connect your MCP client" panel giving the endpoint URL and the no-header `claude mcp add`
command.

**Acceptance test.** HTTP: `/.well-known/oauth-protected-resource` and
`/.well-known/oauth-authorization-server` return the documented fields including
`client_id_metadata_document_supported: true`; a code flow without PKCE is refused; a token minted for a
different `resource` is refused; a valid token resolves to that Human's Member with
`principal.kind = "oauth"`; `gates.approve` with that token is `FORBIDDEN`. Manual:
`claude mcp add --transport http deevy https://…/mcp` with no header, the OAuth dance runs through CIMD, the
consent screen appears, and the tool list loads. If CIMD interop is broken upstream on the day, ship with DCR
enabled and record it in `docs/OPERATIONS.md` as a known limitation rather than holding the slice.

### Walked with a real Claude Code

On 2026-09-06, with Claude Code 2.1.261 against `dev:stub`. The manual half of the acceptance test above had
not been done until then, and it found one thing. Claude Code identifies by CIMD,
`https://claude.ai/oauth/claude-code-client-metadata`, with PKCE S256 and `resource`; its document registers
`http://localhost/callback` and its request redirects to `http://localhost:<ephemeral>/callback`. Better Auth
1.7.2 answered `invalid_redirect`: its matcher granted RFC 8252's port variance to loopback IP literals and
not to the name `localhost`, while its CIMD plugin had accepted that name into the same client row
(better-auth#10937, fixed by #11090 in 1.7.3). The line moved to 1.7.3, which also restored the 1.6 `account`
schema, so migration `0024` drops `account.issuer` and its unique index. With that, the consent page appears,
the tool list loads, and a comment from the session is the Human's in the Event log. `claude mcp add` only
records the server and `claude mcp login` runs the dance, so the documented command gained that second line,
in OPERATIONS.md and on the Settings page.

The list it loaded held four tools a Human can never call, the ones that write a Run, which the handlers
refused one at a time. That became [ADR-0016](../adr/0016-a-run-is-an-agents-and-the-registry-says-which-way-an-operation-faces.md):
a Run stays an Agent's, the registry says so with `agentsOnly`, `tools/list` filters for a Human as it did for
an Agent, and `runs_answer`, `issues_move` and `projects_get` became tools because that is what a Human's own
client is for. [as-yourself.md](../as-yourself.md) is its worked example.

## Slice 8: Slack Channels and routing (M)

**Goal.** Notifications reach Slack, and each Human chooses what reaches them where.

**Depends on.** 2, for the two Run Notification kinds. Nothing in 3 to 7. Build it in parallel.

**Schema.** `channel`: `id`, `workspaceId`, `kind` (`inbox | slack`), `name`, `config` JSON (the incoming
webhook URL), `createdBy`, `createdAt`. `routing_rule`: `id`, `workspaceId`, `notificationKind` nullable
(null is all), `projectId` nullable, `channelId`, `createdAt`. `notification_preference`: `(memberId, kind)`
primary key, `inbox` boolean, `slack` boolean.

**Core.** `deriveNotifications` becomes `route(event)`: compute recipients exactly as today, then consult each
recipient's preferences and the Workspace's routing rules to decide Channels. Inbox rows are written as
today; Slack messages become delivery rows. If slice 5 has landed, reuse `webhook_delivery` with a nullable
`channelId` so there is one retry loop and one claim query; if this slice lands first, it ships a bounded
`deliverDueChannelMessages` in `work.ts` in the same shape and slice 5 generalises it. Decide by which lands
first and say so in the PR. `packages/core/src/slack.ts` builds a Block Kit payload per kind with a link back
to the Issue.

**Operations.** `channels.list`, `channels.create`, `channels.update`, `channels.delete`, `channels.test`
(admin); `routing.list`, `routing.set` (admin); `preferences.get`, `preferences.set` (member, own only).
Events: `channel.created`, `channel.updated`, `channel.deleted`, `routing.updated`.

**UI.** `/settings/channels`: add a Slack incoming webhook with a Test button. `/settings/notifications`: a
per-person matrix of Notification kind against inbox and Slack.

**Acceptance test.** Core with a stubbed fetch: with a Slack Channel and a rule "gate_awaiting to Slack", a
Gate Notification produces one inbox row and one Slack delivery whose payload contains the Issue key and its
URL; a Human who turned Slack off for `gate_awaiting` gets the inbox row only; a Human who turned the inbox
off for `run_finished` gets the Slack message only; a failing Slack POST retries with backoff and exhausts
like a webhook; a rule scoped to one Project does not fire for another. Browser: the Test button posts to a
real Slack channel.

## Slice 9: M2 release, the agent loop (M)

**Goal.** The milestone's own definition of done, on the image.

**Depends on.** 1 through 8.

**Work.** `docs/OPERATIONS.md`: the new env vars (`DEEVY_RUN_STALE_MINUTES`, `DEEVY_SWEEP_INTERVAL_SECONDS`),
the `/mcp` endpoint and its `.well-known` paths, creating an Agent and issuing a key, and how a receiver
verifies `deevy-signature`. `docs/DEVELOPMENT.md`: the dev proxy paths and the `vp run db#generate:auth` step.
An ADR amending ADR-0004 with the `sessionOnly` rule (a Human's own MCP client cannot approve a Gate on their
behalf), and one recording the agent capability field if the shipped design differs from ADR-0004's sketch. A
sample Claude Code loop as an MCP config plus a `CLAUDE.md` snippet in `docs/`: a worked example, not the M4
reference runtime. CI publishes the image to GHCR on a `v0.2.x` tag. `CLAUDE.md` current milestone bumped to
M3.

### Found by writing the acceptance test

An Agent could not find its own work. A trigger opens a Run in `pending`, but `runs.list` was not an MCP
tool, and `inbox.list` is always empty for an Agent because Notifications are derived for Humans only. So
ADR-0003's promise that "Agents without a URL poll their inbox over MCP" did not hold: the only way to learn a
Run's id was a webhook. `runs.list` is now a tool, and an Agent asking for nothing in particular gets its own
Runs, because it has no way to learn its own Member id. The tool set is sixteen, not the fifteen PLAN.md
named, and the snapshot test says why.

**Acceptance test.** On a fresh container from the tagged image: the admin signs in, creates the `planner`
Agent, grants it the deevy Project, and issues a key. A Claude Code loop running outside deevy with that key
over MCP picks up an assigned Issue, reads it and its intent Document, writes the plan Document, posts
Activities as it goes, reaches the Plan Gate and raises a URL elicitation. The Human opens the link, sees the
Gate focused on the Issue page, and approves. The loop resumes, finishes the Run with a summary and a pull
request Link. The inbox and the Slack Channel both show the Run finished, and the Event log tells the whole
story with the Agent as actor and the Human as the trigger one hop away. Stop the container, start the next
tag on the same volume: everything is still there and `/healthz` answers.
